# 个人网站产品路线图

> 状态日期：2026-08-13。本文把网站作为“程序员的公开作品与技术名片”规划；它不是历史实现记录。每完成一项，应在本文件更新状态、验收证据和实际数据。

## 1. 当前判断

网站的工程底座已经完整：内容、实验室、公开 Agent、知识库、管理后台、SEO 静态预渲染、分析和自动发布均已上线。下一阶段的重点不是继续增加通用功能，而是把已有能力转化为可被陌生访客快速理解和验证的个人作品集。

### 已有优势

- 全栈实物：React/Vite 前端、FastAPI/PostgreSQL 后端、Agent、Pi/Mac 节点与 Cloudflare/Aliyun 发布链路都在同一个可运行的 monorepo 中。
- 内容资产：已有 AI 与 Linux 系列文章，支持全文搜索、系列页、RSS、sitemap、结构化数据和预渲染。
- 工程可信度：PR CI、真模型 nightly smoke、Web Vitals、Dependabot、Lefthook 和生产健康检查均已具备。
- 可体验的作品：Agent、Perler、Casino、Pi 状态等不只是截图或简历描述。

### 主要缺口

1. **成果表达不足**：访客能看到文章和实验，但难以在一分钟内知道“我解决过什么问题、如何取舍、结果怎样”。
2. **转化路径不清晰**：首页没有把作品、Agent 体验和联系入口作为主路径；页脚缺少 GitHub、RSS、联系入口。
3. **数据不足以指导取舍**：已有自建分析，但还没有围绕作品、Agent、联系等关键动作的事件漏斗。
4. **公开 Agent 的信任说明不足**：能力、公开/私有边界、文件与图片处理、工具审批和限额应让首次访客可见。

### 数据基线（用于后续对照）

截至 2026-08-13 的生产只读查询，过去 30 天记录 **67** 次 page view；其中首页 **43** 次、`/posts/net-tools` **13** 次。这是小样本，不能据此推断人群偏好；但足以说明先应建立首页到作品/Agent/联系的最小漏斗，而不是引入重型增长系统。

## 2. 产品目标与原则

### 目标

把 `tenggouwa.com` 从“内容与实验较丰富的个人博客”，推进为同时服务以下三类访客的个人技术主页：

| 访客 | 需要在首次访问获得的答案 | 对应入口 |
| --- | --- | --- |
| 招聘方 / 合作者 | 能交付什么，做成过什么 | Projects、案例页、联系入口 |
| 技术读者 | 有哪些可持续阅读与复用的内容 | 文章、系列、RSS、Build Log |
| Agent / 实验体验者 | 能做什么、是否安全、怎样开始 | Agent 说明、Demo、实验室 |

### 原则

- **先包装已完成作品，再新增实验。** 每个公开项目都要有可理解的价值、架构取舍和真实链接。
- **先测量，再扩张。** 延续自建分析；只收集改版是否有效所需的匿名事件。
- **公开与私有边界可见。** 不公开密钥、内部工作区、私有数据或安全绕过细节。
- **保持终端 / CRT 设计系统。** 新页面沿用已有色板、命令提示符、macOS title bar 和无障碍语义。
- **避免伪需求。** 没有稳定内容节奏前，不引入评论、登录体系或邮件 newsletter。

## 3. 优先级路线图

### P0：作品发现与联系闭环

目标：让首次访问者在首页和 About 页面上，能快速理解能力、进入代表作品并完成联系或外链跳转。

| 项目 | 交付物 | 验收标准 |
| --- | --- | --- |
| Projects / Works 页面 | `/projects` 页面；首批 3–5 个可验证案例 | 每项含问题、方案/取舍、技术栈、结果、上线或仓库链接；移动端和键盘导航可用 |
| 首批案例 | Agent 平台、Perler Pattern Maker、Pi/运维或另一项有真实结果的全栈项目 | 不以“技术名词清单”代替结果；不暴露私有配置或敏感数据 |
| 首页路径 | 第一屏后加入 Projects、Agent Demo、代表文章的清晰入口 | 首屏不拥挤；现有文章/实验室入口不消失；视觉通过现有 terminal 规范检查 |
| 身份与联系 | About、页脚和 Projects 统一展示真实 GitHub、邮箱、RSS 与合作 CTA | 修正 About 中的 GitHub 占位链接；所有外链目标正确、可访问、无敏感信息 |
| 转化事件 | 记录 Projects 卡片、Agent 开始/完成、GitHub、RSS、邮箱 CTA 点击 | 事件不含消息正文、邮箱内容、token 或个人身份数据；管理后台可按时间查看 |

**建议交付顺序**：先定案例素材与真实链接 → Projects 页 → 首页 / 页脚入口 → 事件埋点 → 上线后观察两周。

### P1：持续可信度与 Agent 说明

目标：让访客看到当前工作状态和持续的工程实践，同时理解 Agent 的使用边界。

| 项目 | 交付物 | 验收标准 |
| --- | --- | --- |
| Now 页面 | `/now`，由 Markdown 或单一内容源维护；显示更新时间 | 至少包含正在做、最近上线、下一步；无长期过期内容，建议每月检查一次 |
| Build Log / 工程复盘 | 独立内容标签或栏目；优先写 2 篇已发生的复盘 | 候选：Agent research-loop 护栏、Perler 大网格 Worker、生产运维护栏；每篇含问题、决策、验证、边界 |
| Agent 公开说明 | 从 web 或 Agent 首页可达的能力/边界页 | 说明公开和私有能力差异、工具审批、文件/图片处理边界、频率/成本限制与反馈入口 |
| RSS 可见入口 | 在页脚和文章相关区域增加 RSS 订阅链接 | 保持既有 feed 生成逻辑；不引入邮件 newsletter 服务 |

### P2：长期运行质量

目标：以小成本保证公开能力长期可控，而非盲目增加平台复杂度。

| 项目 | 交付物 | 验收标准 |
| --- | --- | --- |
| Agent 成本与异常看板 | 每日调用量、模型 token/费用估算、错误率、拒绝/超时数 | 设置预算或异常阈值；告警不包含 prompt、附件正文或密钥 |
| 前端包体复查 | Admin 图表和低频功能按需加载；记录改前/后体积 | 不影响后台关键路径；优先处理实际首屏或慢网指标，不为消除 warning 盲拆包 |
| 代表实验打磨 | 每季度挑选 1–2 个 Lab 做完善说明或案例化 | 不新增一批缺少目标的 demo；有可分享链接、移动端检查和基本说明 |

## 4. 暂不做

- **评论系统**：当前流量规模下审核与垃圾信息成本大于收益。
- **账号 / 用户体系**：除非 Agent 明确转向面向外部用户的产品，而不是个人站能力展示。
- **邮件 newsletter**：只有确认稳定内容节奏与订阅价值后再评估；目前 RSS 已足够。
- **泛 SEO 改造**：已有 sitemap、RSS、结构化数据、`llms.txt`、预渲染与搜索引擎通知；除非监测到具体问题，不把它作为下一轮重点。
- **更多孤立 Lab**：先把现有作品沉淀成可解释的案例。

## 5. 每项变更的发布检查

1. 与本路线图的目标与非目标逐项对照，确认没有从“个人展示”无意扩展为 SaaS。
2. 先检查真实外链、移动端、键盘访问、空态和隐私文案；再进入编码。
3. 跑项目规定的类型检查、测试和构建；schema 改动同步生成 `packages/api-types`。
4. 通过 feature branch、PR、CI、squash merge 发布；前端发布后在 canonical 域名检查路由、静态 SEO 和埋点。
5. 上线两周后记录事件数据、反馈与下一步结论，避免只凭感觉继续加功能。
