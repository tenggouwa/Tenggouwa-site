“这个模型能跑多少并发？”如果不说明输入长度、输出长度、到达方式、缓存状态和体验门槛，这个问题没有一个可靠数字。

我做过一组固定四卡推理服务的容量实验。既有无 MTP 热态对照的最高通过档为 104；启用原生 MTP，并保持规定的预热与入流条件后，最高严格通过档达到 170，增幅约 63.5%。通过轮次的 TTFT P95 约 1.7 秒，生成速度 P25 约 25 token/s，全部请求完成且零错误。

这个结果属于特定热态工作负载。它不是“随时可以接 170 个任意请求”，也不是已完成的生产收益。这篇文章解释我怎样得到数字、怎样找到失败边界，以及怎样防止实验结论被错误外推。

> 脱敏说明：模型、供应商、加速卡具体型号、机器位置、地址和运行标识均省略。图表为依据历史实验结果重新绘制；部分性能值按展示精度取整。容量 C 表示整套四卡服务的客户端在途上限，不是单卡并发。

## 1. 给容量定义一个质量约束

并发可以是连接数、在途请求数、引擎内活跃序列数，也可以是业务会话数。它们不能互换。

本次实验的 C 指客户端总在途上限。实验要求请求完整收尾、没有取消或错误、引擎不重启，并满足延迟与生成速度门槛。TTFT P95 不超过 10 秒、单请求生成速度 P25 不低于 20 token/s，是本组实验的判定条件。

其中 P25 关注较慢的一部分请求，避免平均生成速度掩盖体验差异。客户端观测的首 token 也应明确是否包含推理片段、排队和网络；不同测量点不能直接拼成一张“模型速度排行榜”。

## 2. 把会改变结果的条件固定下来

本轮使用固定的多轮 Agent 工作负载、四卡张量并行、指定 KV 精度和前缀缓存。对照的核心变化是原生 MTP，草稿 token 数为 5；目标档位对应的调度上限也需要正确配置。

| 维度 | 为什么需要记录 |
| --- | --- |
| 数据集与请求模板 | 决定输入长度、共享前缀与工具调用形态 |
| 采样参数、输出策略 | 改变生成长度和持续占用时间 |
| 引擎、镜像与启动参数 | 决定执行路径、显存和调度行为 |
| 缓存初始状态 | 冷态与热态的 prefill 成本不同 |
| 到达方式 | 瞬时突发与逐步放量的队列形态不同 |
| 收尾规则 | 决定长请求、取消与失败是否被统计 |

对照并不意味着只记住“开了 MTP”四个字。任何镜像、参数或测量规则变化，都应保留在实验记录里，判断它是否仍可比较。

## 3. 把启动参数和实验变量写进同一个记录

讨论 MTP 时只贴一张最终曲线，很难让别人判断是否换了实验条件。下面是历史实验关键参数的脱敏摘录形态，故意不包含权重路径、镜像、设备编号和服务入口：

```text
--tensor-parallel-size 4
--kv-cache-dtype fp8
--max-num-seqs <TARGET_C>
--max-num-batched-tokens 16384
--gpu-memory-utilization 0.78
--speculative-config '{"method":"mtp","num_speculative_tokens":5}'
```

这是特定模型/引擎版本支持下的历史参数记录，不能当作任意模型的通用启动命令；模型专用解析器等也已省略。

`max-num-seqs` 必须与实验目标对齐。旧实验配置默认是 128，若测试客户端把 C 提到 170，但引擎配置仍固定在 128，所测到的是另一种排队系统。后来将这个参数显式化，再继续扫描更高档位。它并不是“把一个并发参数改大就得到 63.5%”。

请求配置也需要同时记录：本轮固定低推理强度、temperature=1、top_p=1，沿用固定输出策略。不同参数改变生成长度后，TTFT 与速度就失去了直接比较前提。

## 4. MTP 与前缀缓存分别在改善什么

MTP 让模型一次提出多个候选 token，再通过验证推进输出。它可能减少逐 token 解码的开销，但候选接受率、额外计算和显存成本都需要实测。草稿数为 5，不代表速度就提升 5 倍。

前缀缓存复用已经计算过的相同输入前缀，主要减少重复 prefill。它也不是任意语义相似文本都能命中；模板、前缀顺序和缓存生命周期都会影响效果。

两者与调度、到达方式存在相互作用。因此本次结论是“这组配置在固定条件下达到了这个容量”，不能把所有改善机械地分摊成 MTP 几成、缓存几成。

![热态容量验证中的预热、缓存与 MTP](https://tenggouwa.com/images/engineering-cases/inference-experiment-flow.svg)

## 5. 为什么采用分阶段入流

实验先以 16、32、55 个在途请求逐步进入服务，再运行目标档，每个前置阶段持续约 90 秒，目标阶段持续 600 秒。首阶段前重置前缀缓存，并记录预热过程。

这能验证长期运行、前缀已热、入口平滑放量时的可运营容量。它也刻意没有证明冷启动后立刻涌入同样流量的表现。

目标阶段停止发压后，还要等待在途请求排空。某轮有多少请求最终完成，必须连同发压窗口和排空时间报告。不能把包含排空的完成数直接除以 600 秒，当作纯发压吞吐。

## 6. 怎样写一份不会悄悄改变缓存条件的 runner

下面是根据实际 runner 结构重新组织的伪代码：

```python
stages = [(16, 90), (32, 90), (55, 90), (target_c, 600)]
for index, (concurrency, duration_s) in enumerate(stages):
    result = run_benchmark(
        dataset=frozen_fixture,
        concurrency=concurrency,
        arrival_rate=concurrency / 20,
        duration_s=duration_s,
        drain_timeout_s=180,
        reset_prefix_cache=(index == 0),
    )
    save_stage_exit_code(result.exit_code)
    assert result.exit_code == 0
    assert result.errors == 0
    assert result.cancelled == 0
```

前置阶段共享同一个引擎和前缀缓存，只有第一阶段前重置。若每阶段都重启模型，或者到目标阶段又清空缓存，实验就变成冷态测试；若预先偷偷运行额外流量，又会改变热态起点。

这里同时给了到达速率和在途上限：C170 的名义发压速率是 8.5 请求/秒，但这个数不能直接作为完成吞吐。客户端并发限制、请求持续时间、长尾和排空都会改变实际完成数。必须从逐请求时间戳计算实际窗口。

## 7. 先找通过档，再验证失败档

![固定热态条件下的容量边界与质量门槛](https://tenggouwa.com/images/engineering-cases/inference-capacity-results.svg)

历史结果中，无 MTP 热态最高通过档为 C104，C108 未通过。MTP 方案持续上探，最终得到如下关键点：

| 档位 | TTFT P95 | 生成速度 P25 | 结果 |
| --- | ---: | ---: | --- |
| C144 | 约 2.84 秒 | 约 29.61 token/s | 通过 |
| C160 | 约 2.45 秒 | 约 27.61 token/s | 通过 |
| C168 | 约 1.47 秒 | 约 27.20 token/s | 通过 |
| C170 | 约 1.66 秒 | 约 25.43 token/s | 通过 |
| C171 | 约 16.94 秒 | 约 14.30 token/s | 未通过 |

C170 轮次最终 1,604/1,604 完成，零取消、零错误。C171 虽然也全部完成，但延迟和速度都越过门槛，因此不能称为可用容量。

局部档位的延迟没有单调递增，不意味着可以推导出“并发越高越快”。缓存复用、调度批次和入流阶段会改变分布。这些是离散实验观察，不是平滑性能曲线。

`(170 - 104) / 104 ≈ 63.5%` 表示最高已验证热态达标并发的提升，不表示 tokens/s、收入或 GPU 利用率也同步提升了 63.5%。

## 8. 没有 OOM，仍然可能已经超过容量

C171 的证据更指向首波长上下文 prefill 与 admission 造成的尾延迟，而不是显存耗尽或引擎重启。

这意味着继续增加并发未必会先得到一个明显的崩溃。更早出现的可能是等待时间陡增、较慢请求的解码体验恶化，以及客户超时。只用容器 healthy、HTTP 200 或“全部最终完成”来判断，就会错过业务容量边界。

还要区分入口排队与引擎内部排队。把等待移到网关，可以获得更明确的控制和观测，但不会凭空消除客户等待。端到端体验仍然需要计入这段时间。

## 9. 热态通过，不代表冷态通过

这组实验里，C170 的首分钟仍存在约二十多秒的尾延迟；冷态严格交互的既有通过基线仍为 C55。因此，热态容量与冷态默认承诺必须分开。

若要工程化，入口可以从较低档位启动，使用真实模板预热，再通过观测逐级升档。引擎重启、缓存失效或流量形态改变时，应降低档位重新验证。

这些放量、排队和自动降档机制在当时形成了生产化提案，不能写成已经全部上线。即使照此实现，最终仍要做真实入口、混合模型和长时间运行验证。

## 10. 不能只靠压测工具最后一行判断通过

实际工装曾用正则解析完成数。完成数变成 `1,469` 这样的带千位分隔形式后，旧解析器没有正确识别，导致数值门禁误判。

解析代码至少应接收这种格式，并与结构化导出的总数交叉检查：

```python
import re

m = re.search(r'completed=([0-9][0-9,]*)', log_line)
if m is None:
    raise ValueError('missing completion count')
completed = int(m.group(1).replace(',', ''))

assert completed == exported_unique_completed
assert not duplicate_request_ids
assert cancelled == 0 and errors == 0
```

修完解析器，还要完整重跑受影响档位；不能只改一条日志让它通过。

此外，进程退出码与业务质量门禁是两个检查。退出码零说明工具完成了工作，不说明 P95 达标。C171 全部完成、却延迟和生成速度不达标，就是最直接的反例。

## 11. MTP 和缓存计数怎样交叉核验

历史实验某个通过档位中，MTP 接受 token 计数差分约 163 万，草稿计数差分约 447 万，接受比例约 36.6%。这可以说明存在实际草稿与接受行为，但不能直接推出端到端加速倍数。

计数器应取同一轮开始和结束的差分：

```text
accepted_delta = accepted_end - accepted_start
draft_delta    = draft_end - draft_start
acceptance     = accepted_delta / draft_delta

wall_throughput = total_completed_output_tokens / measured_wall_seconds
```

如果引擎中途重启，计数器可能重置，这轮应标记异常，不能直接相减。如果监控还包含其他请求，也需要隔离或明确共享流量的影响。

C170 的缓存输入占比约 82.62%，也是特定字段口径下的 token 比例，不能直接称为“82.62% 的请求命中缓存”。一次命中很长前缀的请求与一次命中很短前缀的请求，权重并不相同。

## 12. 把成功条件与失败边界做成可执行检查

对于每个目标档位，最小判定可以写成：

```python
passed = (
    completed == submitted
    and errors == 0
    and cancelled == 0
    and engine_restarts == 0
    and ttft_p95_s <= 10
    and request_speed_p25 >= 20
)
```

但计算分位数之前，还需要明确统计总体。如果只对正常返回的请求计算 P95，同时把超时样本从分母删除，就可能让一个失败很多的档位看起来很快。因此报告先列完成、错误和取消，再解释可计算时延的样本范围。

本轮对 C170、C171 及更高档位都保留结果，避免只挑最漂亮的一轮。C171 的失败并没有被“最终全部完成”抵销，冷态首波尾延迟也没有被热态全局 P95 隐藏。

## 13. 容量报告还需要哪些原始证据

我会为每轮保存数据集标识、启动配置、阶段时间、退出码、完成与取消数、逐请求延迟、速度分布、缓存与 MTP 计数、GPU/宿主遥测和服务日志。

工装也可能出错。本轮曾遇到完成数超过千条后带千位分隔符，脚本没能正确解析的情况。修复数字解析后，需要重新验证受影响轮次，不能把工具误判当成引擎失败，也不能忽略真正的失败退出码。

这些证据应留在受控环境中；公开文章保留聚合结果和方法，不发布原始业务请求或部署细节。

## 14. 真正上线时，还缺哪些验收

实验完成以后，工程化提案提出了从低档位预热、逐级放量、观察后升档，以及异常降档的路径。以下是提案层面的状态图，不是已经上线的证明：

```text
启动 / 缓存重置
  → 保守档位
  → 真实模板预热
  → 持续观察延迟、错误和缓存
  → 逐级升档
  → 触发门槛时退回低档并重新验证
```

落地之前还需要验证真实网关入口的排队预算、多个模型是否争用资源、分布变化时的降档、重启恢复和长时间稳定性。入口队列还必须受总 deadline 约束，不能用“排队成功”掩盖客户等待。

这些工作与“实验跑到 170”属于不同交付阶段。在复盘里把两者分开，反而能让别人清楚知道成果已经到哪一步，以及接下来需要什么证据。

## 15. 这项成果能怎样用于业务决策

它能帮助确定热态入口上限、评估升级与调参收益，并为算力采购提供实验依据。若要进一步声称节省成本，需要补上功耗、硬件费用、代表性流量、峰谷比例和稳定运行数据。

我从这轮实验学到的是：容量数字必须附带适用条件和失败边界。一个能够说明什么时候失效的结果，才适合交给上线和商务团队使用。
