客服 Agent 最让人烦躁的错误之一，是反复要求客户做已经做过的事情。客户说“订单号前面发过了”“这些步骤都试过了”，系统却继续追问。

我在一个智能客服项目中推进过这类问题的治理。固定 500 条历史会话的完整回归中，上下文类失败从 39 条降到 12 条，减少约 69%；整体通过数从 399 条增加到 409 条。这两个数字需要一起看：一种错误明显减少，并不意味着系统的全部问题都已解决。

> 脱敏说明：本文不展示真实会话、品牌、产品、订单、客户或内部标识。所有对话与 JSON 示例均重新构造。结果是历史离线回放评测，不代表线上自动解决率；后续方案建议与已验证改动分别说明。

## 1. 聊天记录传进去了，为什么仍然像失忆

一个常见实现是把最近几条消息和知识库片段一起放进 Prompt。模型理论上能看到上下文，但“能看到”不等于“系统已经记住”。

同一段历史里可能混有客户自述、客服建议、系统通知和工具返回。如果不区分来源，模型可能把“请上传照片”理解成“已经收到照片”，把“可以申请修改地址”理解成“地址已修改”。

长历史还会带来主题漂移。客户上一轮说设备无法连接，本轮补一句“都一样”，不能把这句短语当成一个全新问题；也不能因为最近出现了订单号，就忘记当前主诉。

这类问题需要先明确状态和来源，再让模型组织语言。

## 2. 把三种记忆分开

| 信息 | 适合保存在哪里 | 为什么 |
| --- | --- | --- |
| 产品说明、批准的排障 SOP | 可追溯知识库 | 内容相对稳定，需要版本和来源 |
| 客户已确认的型号、已执行步骤、材料状态 | 会话状态 | 只属于当前会话，会持续变化 |
| 订单、物流、退款与实际操作结果 | 授权业务工具 | 有时效与权限，不能靠静态文档推断 |

如果客户已经执行了重启，补更多“怎样重启”的知识，不会解决重复追问。如果订单状态更新了，让模型记住旧聊天，也不能代替实时查询。

这个划分让我更容易判断修复归属：是缺知识、丢状态，还是没有拿到被授权的实时事实。

## 3. 给事实保存来源，给材料保存状态

我参与的改动将客户确认的型号、主诉、已执行步骤、限制条件、材料请求和服务状态归并到版本化会话状态。历史会话缺少状态时，回填也必须遵循来源边界。

下面是重新构造的教学结构，不对应项目真实字段：

```json
{
  "version": 1,
  "topic": "device_connection",
  "facts": {
    "model": {"value": "device-A", "source": "customer", "confirmed": true},
    "order_reference": {"provided": true, "verified_by_tool": false}
  },
  "steps": {
    "power_cycle": {"state": "completed", "source": "customer"}
  },
  "materials": {
    "label_photo": {"state": "requested"}
  },
  "service": {"state": "ai_active"}
}
```

这里刻意区分“已经提供订单信息”和“业务工具核验成功”。客户说“地址已经改了”，可以记录为客户自述；只有授权接口确认，才能把它当成业务事实。

材料也不能只用一个含糊的布尔值。尚未请求、已请求、已提供、客户无法提供，是不同状态。把“被要求提供”误判成“无法提供”，会错误地改变后续处理路径。

订单、联系方式等敏感原值不应因为“做记忆”而复制进不必要的模型上下文；很多重复追问保护只需要一个已提供标记。

## 4. 会话状态应当怎样更新，而不是只保存一个 JSON

实际代码中的状态既有跨轮保留的数据，也有只对本轮有效的数据。如果两类信息混在一起，客户上轮提供了联系方式，下轮问新的故障时，系统可能仍把它当作“正在补充联系方式”。

我把这个问题拆成两个生命周期：`provided_fields` 这类历史标记持续保留，`current_turn` 这类本轮信号每轮重建。以下是改写后的最小 reducer，演示更新顺序：

```python
from copy import deepcopy

def reduce_turn(previous, event):
    state = deepcopy(previous)
    state['current_turn'] = {
        'newly_provided': [],
        'customer_reports_resolution': False,
    }
    if event['role'] == 'system':
        return state
    if event['role'] != 'customer':
        return state  # 客服发言由另一条有来源约束的路径归并

    if event['context_relation'] == 'standalone':
        state['issue']['completed_steps'] = []
        state['issue']['constraints'] = []
        state['issue']['missing_fields'] = []

    for field in event['recognized_provided_fields']:
        if field not in state['provided_fields']:
            state['current_turn']['newly_provided'].append(field)
        state['provided_fields'] = sorted(
            set(state['provided_fields']) | {field}
        )
    return state
```

这是机制示例，省略了输入校验、版本升级和业务工具验证。真实更新还要处理主题承接、附件、语言决策、客户报告的操作，以及服务状态。

`context_relation` 来自明确的分诊结果，不应靠判断正文是否包含一句固定话来识别评测样本。客户短句有可能承接前文，也有可能开始新主题，系统需要把识别结果和来源保留下来，而不是在回放脚本中临时“修正答案”。

## 5. 产品切换时，哪些状态该清、哪些该留

如果客户先问设备 A 的排障，再切换到设备 B，直接沿用全部状态，会把 A 的步骤带进 B；清空全部状态，又会忘记客户已提供的联系方式。

实际实现中存在专门的产品切换重置路径：清除产品型号、产品相关排障步骤和待补信息，保留允许跨产品沿用的非敏感引用标记、服务状态与语言。

| 状态 | 同产品追问 | 明确换产品 | 原因 |
| --- | --- | --- | --- |
| 已提供订单引用标记 | 保留 | 按许可保留 | 标记不等于订单与新产品已关联 |
| 产品型号 | 保留已确认值 | 清除/重新确认 | 不能把旧型号套到新设备 |
| 已做排障步骤 | 保留 | 清除产品相关项 | 不同设备的动作含义可能不同 |
| 待补贴纸/视频 | 按当前问题保留 | 重新建立 | 材料请求属于具体处理流程 |
| 人工接管状态 | 由状态机决定 | 继续由状态机决定 | 产品切换不能偷偷恢复 AI 回复 |

这张表也可以直接成为测试矩阵。测试不只看回答里有没有“重启”，而要检查内部状态是否正确，以及模型上下文是否携带了不该存在的旧事实。

## 6. 生成回答之前，先决定本轮做什么

![从输入角色到回复计划的客服处理链](https://tenggouwa.com/images/engineering-cases/support-state-pipeline.svg)

服务端在每轮生成前构建回复计划：当前主诉是什么，哪些事实已知，哪些材料缺失，是否有批准的下一步，需要知识检索还是业务工具，以及当前能否由 AI 继续回复。

例如，这段虚构对话：

> 客户：设备连不上，我已经断电重启过，订单信息也发了。  
> 后续消息：还是一样。

合理计划应保留“连接问题”，排除再次索取订单与重复断电，检查是否存在未执行且有依据的下一步。没有批准的 SOP 时，应说明证据边界，并按流程建议人工接续。

计划不能只写“不要重复”。它需要明确列出允许追问的未知项和禁止重复的已知项。这样才能对输出做确定性的校验，也能解释一次追问为什么发生。

在实现中，普通接口与流式接口使用同一计划，避免两条路径各自演化。结束确认也可以使用确定文案，无须每次调用模型重新发明一种结束方式。

## 7. 一个回复计划，应当能解释为什么允许追问

回复计划本身应当是数据。实际的轻量计划对象包含 action 和可选缺失字段，调用方用它约束上下文与确定性回复。下方简化了名称：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class TurnPlan:
    action: str
    missing_field: str | None = None

    def context_payload(self):
        return {
            'action': self.action,
            'missing_field': self.missing_field,
        }
```

关键并不是类定义，而是决定依据。当前可确认已解决、正向反馈、结束确认和引用歧义等情形，会形成不同计划；普通问题仍由模型回答。它没有授权随便查询订单，更不会仅凭一个语义标签就执行退款或建立人工工单。

以重新构造的三轮例子说明：

```text
T1 客户：设备无法连接，我已经重启，订单信息已提交。
T2 客户：照片稍后补，我现在不在设备旁边。
T3 客户：还是不行。
```

第三轮的状态应能解释：主诉仍是连接问题，重启已执行，订单引用已提供，照片尚未提供且有暂时无法提供的限制。它不能把“稍后补”变成“已收到”，也不能把“订单已提交”变成“订单已核验”。

如果本轮还缺关键证据，追问必须能映射到该缺失字段。若缺的是批准的处理 SOP，继续收集无关字段也不会创造一个处理办法，应明确知识或权限边界。

## 8. 人工状态与系统事件要由系统决定

“我建议你联系人工”和“已经为你转接人工”有完全不同的业务含义。前者是建议，后者要求队列中确实存在相应状态。

我处理的链路将显式人工请求与真实服务状态关联，避免模型凭语言承诺“已安排专员”。系统通知、机器人控制消息、撤回事件，也不再被当作新的客户问题。

角色应来自明确的数据字段。不能因为文本里出现“您好”，就猜它来自客服；也不能把一条系统事件的展示标签当作可靠角色。如果源数据契约不完整，需要标记数据质量问题，不能全部算成模型错误。

## 9. 事务与来源约束，决定下一轮是否真的记住

状态如果只在生成前更新于内存中，模型回答失败或服务重启之后，下一轮仍会丢失。该项目把状态保存在工单的版本化载荷里，并与会话/事件的事务边界结合。

下面表达的是期望的数据一致性关系，并非宣称所有表都在一条 SQL 中：

```text
客户消息持久化
  → 归并会话状态
  → 保存本轮计划与相关事件
  → 按实际服务链路生成并保存回复

必须避免：回复声称“已经收到材料”，持久状态却没有对应来源。
```

从旧会话回填时，同样不能信任每一句客服自然语言。例如旧回复说“我们已经安排了”，没有真实状态或工具事实，就不能写成 `human_assigned = true`。允许回填的事实种类、来源角色和作用域都应明确。

这项机制也有边界：部分输入识别依赖模式和配置，仍可能识别不全。它能让状态和失败更可检查，但不能证明已经拥有通用、无误的长程记忆。

## 10. 如何设计不会自我欺骗的回放

最小评测单元不应只有一个问题和一个参考答案，还需要观察截断位置、上下文角色、已选产品、授权事实与允许动作。以下是完全虚构的 fixture：

```json
{
  "case": "synthetic-repeat-order",
  "history_before_target": [
    {"role": "customer", "text": "订单信息已经提供"},
    {"role": "staff", "text": "请补充设备贴纸照片"}
  ],
  "target": {"role": "customer", "text": "现在不方便拍"},
  "expected": {
    "must_not_request_again": ["order_reference"],
    "must_not_claim": ["photo_received", "order_verified"],
    "service_state": "ai_active"
  }
}
```

真实评测采用冻结、脱敏的数据，而不是这个示例。每次回放只允许看到目标客户消息之前的信息；真实客服之后的答案可以供人工参考，不能进入模型上下文。

我会先运行确定性检查，例如是否编造人工状态、是否泄露受控字段，再让语义 Judge 判断回答是否承接主诉。不一致或不可用的评审要进入人工复核，不能为了凑通过率修改源对话。

还要保留分类迁移。39 → 12 是“上下文失败标签”的减少；如果样本从 context 变成 knowledge_missing，它仍然没通过。完整结果表比一份只罗列修复成功案例的报告更有解释力。

## 11. 为什么只重跑修好的 bad case 不够

只重跑上一轮失败样本，适合快速定位，却会漏掉回归：为一个场景增加规则，可能伤害另一个场景；评审器也可能把同一问题改分到其他类别。

本次固定 500 条会话的完整结果如下：

![固定 500 条会话中的上下文失败与整体通过数](https://tenggouwa.com/images/engineering-cases/support-evaluation-results.svg)

| 指标 | 修复前 | 第二轮完整回归 |
| --- | ---: | ---: |
| 通过 | 399 | 409 |
| 失败 | 93 | 83 |
| 待复核 | 8 | 8 |
| 上下文类失败（属于失败子集） | 39 | 12 |

按 500 条固定分母计算，整体通过比例从 79.8% 到 81.8%，增加 2 个百分点。上下文失败减少 27 条，但通过仅增加 10 条，说明部分样本仍被其他缺陷阻挡。不能把分类减少直接等价为客户问题已解决。

后续还有定向修复，但它们发生在这次完整回归之后，不能直接加进 409 这个结果。要更新整体指标，必须再跑同一完整数据集。

## 12. 评测本身也需要版本管理

项目后来建立了 1,000 条已映射真实会话的多模型评审基线，严格通过率约 80.1%。这个结果比旧单模型报告低，并不直接代表产品退步：评审协议、语言判断与分类规则同时发生了变化。

比较前后结果时，至少要固定数据集、回放位置、允许看到的历史、回答模型、评审协议和排除规则。尤其不能把客户发言之后的真实客服答案塞回输入，那会造成未来信息泄漏。

我的评测习惯是把失败拆成上下文、知识缺失、工具权限、语言、幻觉与评审不可用等类别。暂时无法评审就保留待复核，不把它自动计为通过。

高风险错误也不该被平均分淹没。无依据的退款承诺、隐私泄露或虚假转人工，即使数量少，也需要独立阻断和人工复核。

## 13. 从离线改善到业务收益，还差什么

这轮验证证明了固定样本中一类上下文错误显著减少。它没有直接证明客服人数减少、客户满意度上升或退款周期缩短。

要建立这些业务结论，需要继续采集线上重复追问率、客户补充材料次数、人工接续后的信息重复索取、实际解决结果和处理时长，并通过一致口径比较。

对我而言，这个项目最关键的认识是：客服 Agent 应当把已知事实、允许动作和真实服务状态交给系统管理。模型负责表达，但不独自承担记忆、权限和操作结果的全部责任。
