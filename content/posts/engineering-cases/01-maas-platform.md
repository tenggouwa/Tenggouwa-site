调用模型最容易展示的部分，是输入一句话，再把流式答案显示出来。真正对客户提供服务以后，困难会转移：谁有权调用？余额不足时怎么办？供应商失败后能否重试？答案返回了但用量没有回来，这一笔应当怎样处理？

我参与推进过一个面向真实客户的多模型服务平台。我的工作跨越接口接入、管理控制台、请求准入、计费对账和生产问题治理。这篇文章沿着一条请求，解释这些环节为什么必须连起来，以及我在其中形成的判断。

> 脱敏说明：本文省略组织、客户、供应商、模型身份、地址、商业报价与原始日志。配图重新绘制，只表达逻辑关系，不对应实际部署拓扑。文中的伪代码用于解释设计，不是生产代码摘录。

## 1. 先定义平台究竟承诺什么

“兼容某种 API”只是入口约定。客户真正依赖的是一个稳定的公开模型标识、一组可验证的能力、清楚的限额，以及可核对的账单。

例如，两个供应商都能接收聊天请求，不代表它们都支持工具调用、结构化输出、图片输入或者相同的参数组合。把一个请求原样转发出去，可能在普通聊天中成功，在 Agent 连续调用工具时失败。

我在处理接入问题时，逐渐把配置分成三件事：公开能力是什么、底层部署实际能做什么、当前允许哪些组织使用。新增一个部署，不应自动等于对所有客户宣布一项能力。

| 对象 | 要回答的问题 | 典型错误 |
| --- | --- | --- |
| 公开模型 | 客户调用什么、得到什么能力 | 名字相同，能力悄悄变化 |
| 底层部署 | 由谁承接、参数怎样适配 | 把供应商差异泄漏给客户 |
| 组织授权 | 谁能调用、额度和限额是多少 | 知道模型 ID 就能使用 |
| 已发布配置 | 数据面此刻执行哪个版本 | 控制台保存成功，却没有生效证据 |

配置编辑、配置发布、应用镜像发布，是三个不同动作。后台显示“已保存”，并不足以证明线上请求已经执行新配置。

## 2. 将控制面与数据面分清

![MaaS 的控制面、数据面与账务闭环](https://tenggouwa.com/images/engineering-cases/maas-overview.svg)

控制面负责管理模型、部署、权限、价格与路由，并形成可追踪的发布版本。数据面负责执行已经发布的配置，完成鉴权、准入、供应商调用和返回。

这样划分以后，一个常见的需求——“接入新供应商”——就可以被拆成可验证步骤：录入密钥引用，登记能力，配置采购与销售规则，建立路由，执行验证，再发布并检查运行回执。前端不持有供应商密钥，也不承担决定真实路由的职责。

这种分层并不要求一开始就拆出大量微服务。它首先是一种责任边界：谁决定配置，谁执行配置，谁能证明版本生效。

## 3. 把请求、供应商尝试和资金记录拆成三种实体

落到数据库设计时，最容易混淆的是“一次请求”。客户端发来一个请求，平台可能尝试两个供应商；第二次尝试成功，不意味着平台产生两笔客户销售。

下面是从实际问题中抽象出的最小关系。名称和字段经过改写，省略索引与其他业务列：

```sql
-- 结构示意，不能直接替代完整生产迁移
CREATE TABLE call_record (
    id text PRIMARY KEY,
    account_ref text NOT NULL,
    config_version text NOT NULL,
    outcome text NOT NULL
);
CREATE TABLE provider_try (
    id text PRIMARY KEY,
    call_id text NOT NULL REFERENCES call_record(id),
    try_no integer NOT NULL,
    outcome text NOT NULL,
    upstream_started_at timestamptz,
    first_content_at timestamptz,
    UNIQUE (call_id, try_no)
);
CREATE TABLE budget_hold (
    call_id text PRIMARY KEY REFERENCES call_record(id),
    reserved numeric NOT NULL,
    actual numeric,
    outcome text NOT NULL
);
```

这里 `budget_hold.call_id` 唯一，是“同一平台请求只有一个逻辑预占”的表达。实际实现还需要处理客户端幂等键如何绑定平台请求、重复请求返回什么、重试时是否复用已完成结果，不能只靠这张表解决。

一次脱敏后的时序可以写成：

```text
call-A
  hold-A：已预占
  try-1：首字节前返回可重试错误
  try-2：成功，取得完整 usage
  call-A：记录响应结果
  hold-A：依据确认金额结算一次
```

第一笔失败尝试是否产生采购费，由供应商事实决定，不能因为客户没有收到内容就擅自记零。于是同一条业务链会有两种汇总方向：客户销售按逻辑请求核对，采购按供应商尝试核对。

## 4. 请求级配置快照怎样避免“执行到一半换规则”

如果每一步都读取可变的最新配置，会出现难以解释的状态：路由按版本 A 选供应商，结算按版本 B 的售价算金额，事后再用版本 C 的名称展示。

我的处理思路是把已发布版本和价格快照绑定到本次请求/尝试。下方伪代码解释边界，不是完整的转发器：

```python
runtime = load_published_version()
identity = authenticate_api_key(request)
model = runtime.require_model(request.model)
candidates = runtime.authorized_candidates(identity, model)
validate_capabilities(request, model)

sale_snapshot = resolve_sale_price(identity, model, runtime)
hold = reserve_budget(request.id, sale_snapshot)

for candidate in candidates:
    purchase_snapshot = resolve_purchase_price(candidate, runtime)
    attempt = start_attempt(request.id, candidate, purchase_snapshot)
    # 参数适配、实际转发和响应生命周期由独立模块处理
```

版本化配置也不等于冻结所有安全状态。凭据撤销、成员停用等授权信息仍需在请求开始时正确校验。需要稳定的是本次执行规则和金额解释，不能把旧授权快照当成永久通行证。

能力校验同样要在上游调用前做。对于明确不支持的参数，应返回可解释的错误；对于已经验证可安全移除的兼容参数，才执行显式适配。不能为了提高表面兼容率，静默删除可能改变用户意图的字段。

## 5. 在请求到达模型之前完成准入

对一次调用，我需要在调用供应商前回答三个问题：身份是否合法，权限是否满足，当前预算和容量是否允许继续。

其中额度预占尤其容易被低估。生成完成前无法知道最终输出量，若等调用结束才检查余额，多个并发请求可能同时透支。预占是为在途请求保留预算；最终结算再依据有效用量处理差额。

但预算预占本身也会进入关键路径。历史记录增长后，余额汇总和客户行锁可能拖慢所有同客户请求。这是后续[钱包锁竞争案例](/posts/wallet-row-lock-and-history-scan)的起点：一个为资金正确性设置的保护，如果临界区太大，会变成可用性瓶颈。

并发限制同样要覆盖多个实例。单进程计数器只能约束本进程；多实例需要共享租约或其他可证明的一致性机制。实例退出后也必须能够回收租约，不能永远占住容量。

## 6. 故障切换必须有流式边界

调用上游之前失败、尚未开始向客户输出时失败、已经输出一部分内容后失败，是不同的场景。

在实际网关中，我关注的是供应商首字节前的可切换窗口：对符合规则的限流、服务端错误或超时，才尝试下一个候选。开始流式内容后，不再把另一个供应商的输出拼进原答案。

假设一个模型已经给出半段工具参数，另一个模型从头生成不同参数，客户得到的内容即使仍是合法文本，也可能已经破坏业务语义。重试策略必须服从响应协议和操作副作用，而不只是追求更高的 HTTP 成功率。

同样，不能对所有 4xx 重试。权限不足、参数非法和余额不足，重复调用通常不会改变结果，反而增加负载和费用。

## 7. 流结束、请求成功与结算完成要分别记录

![请求完成与账务确认是两个相互关联的维度](https://tenggouwa.com/images/engineering-cases/maas-lifecycle.svg)

流式链路中至少存在几类证据：上游结束标记、有效用量、下游终止帧、HTTP 连接关闭，以及账务写入结果。只看到连接关闭，就把请求一律标成取消，会污染成功率和排障判断；只看到上游结束，就宣称客户一定收到了完整答案，也超出了证据。

我参与处理过这类终态问题，包括并发资源重复释放、完成流被误记取消和未启动流的连接释放。它们看起来像日志问题，实际影响的是容量统计、客户解释和对账。

设计上，我更愿意保留“响应处理结果”和“账务确认状态”两个维度。已观察到用量，但供应商成本尚未最终确认，应记录待确认，而不是填一个零成本让报表看起来完整。

## 8. 怎样给流式资源找到唯一的收尾责任人

实际修复里，并发 Gauge 曾可能从多个异常路径被重复扣减。正常结束、生成器退出、下游断连和兜底清理都可能执行清理，因此资源释放必须幂等。

```python
# 与实际修复相同的幂等思想，名称和上下文已简化
from threading import Lock

class Lease:
    def __init__(self, release):
        self.closed = False
        self.lock = Lock()
        self.release = release

    def close(self):
        with self.lock:
            if self.closed:
                return
            self.closed = True
        self.release()
```

锁保护一次性标记，真正释放在锁外执行。实际实现还需明确释放回调失败时的资源处理与告警；它只解决“一次性收尾”，不解决“何时算业务成功”。

另一个容易漏掉的分支是：上游连接已经建立，但下游响应生成器还未开始迭代，客户端就离开。仅把清理写在生成器内部的 `finally`，可能根本没有机会执行。因此连接、租约和响应关闭回调都要明确归属，并检查尚未开始输出的路径。

我把验收矩阵拆成下面几类，逐条看终态与资源：

| 场景 | 必须检查的证据 | 不能遗漏的资源 |
| --- | --- | --- |
| 首字节前失败 | 失败尝试、重试资格、候选顺序 | 失败连接与该尝试租约 |
| 输出后断流 | 已输出事实、错误原因、用量完整性 | 上游连接与模型并发 |
| 终止帧正常发送 | 终止帧发送路径、上游完成与账务结果 | 请求级在途计数 |
| 生成器未启动即关闭 | 未启动分支是否仍有连接 | 已建立但无人消费的上游 |
| 多个清理入口同时触发 | 释放仅发生一次 | Gauge 不得变成负数 |

“终止帧已发送”是平台观察到的交付证据，不是终端设备展示成功的证明。这个区分应保留在诊断语义里。

## 9. 价格必须属于那次请求

如果账单查询永远读取当前价格，调整报价后，历史请求的金额可能随之改变。请求需要关联当时的价格快照；后续供应商确认、补账和人工调整也需要保留来源。

客户请求与供应商尝试不是一对一关系。一个客户请求可能经过多个候选尝试，因此销售汇总、采购汇总和尝试数不能混用分母。内部测试、健康探测与外部客户销售也应分别统计。

我在经营报表中处理过这些差异：最新入账和历史快照有优先关系，未知金额单独披露，旧周期因补账需要重述。它使平台能够解释“这笔钱从哪里来”，也避免把暂估毛利误说成净利润。

## 10. 经营统计怎样避免把重试算成增长

下面是一个重构后的汇总例子。它首先要求销售事实已经归一为一请求一条，不直接把尝试表连接进来：

```sql
-- 教学示意：amount NULL 保留为未知，不回填 0
SELECT
    count(*) AS customer_calls,
    sum(amount) AS known_sales,
    count(*) FILTER (WHERE amount IS NULL) AS unknown_sales_calls
FROM confirmed_call_sales
WHERE business_time >= :window_start
  AND business_time < :window_end
  AND organization_kind = 'external_customer';
```

采购另从尝试事实汇总，再与销售结果在报表层组合。若先把客户请求与多个尝试 JOIN，再对销售金额求和，一个发生重试的请求就可能被重复累计。

同样，`SUM` 忽略 NULL 不等于未知成本不存在。报表必须同时展示未知条数。补账后重算上期，也应明确它是重述后的比较基线，而不是偷偷改掉上次发布的快照。

这些细节让我把“平台可运营”理解成一组可核对的数据契约，而不只是多了几个管理页面。

## 11. 发布验收应沿着客户请求走一遍

我的验收思路是覆盖一条完整业务链，而不只检查进程存活：

1. 配置版本已经生效，目标组织有正确权限。
2. 普通请求、流式请求和所声明的能力能够使用。
3. 不合法请求被正确拒绝，且没有意外调用供应商。
4. 成功、取消、超时等路径都能释放资源。
5. 请求、供应商尝试、用量和金额能够关联。
6. 旧版本存在明确的回滚路径。

付费模型冒烟还需要调用次数与费用预算，不能让发布门禁无限调用上游。普通冒烟与完整回归承担不同责任，报告必须写清执行了哪一类。

## 12. 我能证明的成果与仍需谨慎的地方

这套平台承接过真实客户请求和计费业务。我能具体说明自己推进的接口、准入、账务与排障工作，也能用后续文章中的隔离实验和发布采样解释改进。

但业务销售增长包含渠道、客户需求、定价与供应商等因素，不能全部归到技术优化头上。短时发布采样没有错误，也不等于已经证明了月度 SLA。

这个项目对我的价值，在于我开始把一条模型调用看成一条完整业务责任链：配置有版本，调用有权限，容量有边界，结果有证据，金额有来源，发布有验收。
