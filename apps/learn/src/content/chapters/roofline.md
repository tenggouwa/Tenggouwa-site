### 为什么 GPU 很强，模型仍然不够快

上一课解决了“怎么量”。现在假设你发现某个负载吞吐较低，第一反应可能是换更强的卡，或者把 batch 调大。但 GPU 的“强”不只有一个维度：算术单元能做多少计算、内存能多快供给数据、程序能否组织足够并行工作，都很重要。

本课用一个简化模型拆开前两个因素。它不替代 profiler，而是帮助你先提出有方向的假设。例如：如果主要时间花在读取权重，那么只减少几次加法可能几乎没有效果。

### 计算与搬运，是两本不同的账

一次矩阵乘法要从内存读输入和权重，执行乘加，再写输出。设需要 F 次浮点操作，有效计算峰值上限用 P 表示；从 HBM（GPU 的高带宽设备内存，权重和 KV 主体通常存放于此）搬运 Q bytes，带宽上限用 BW 表示。

如果只考虑计算，至少需要 `F/P` 秒；如果只考虑内存，至少需要 `Q/BW` 秒。假设两者能充分重叠，整个操作仍不可能快过较慢的一项，因此乐观下界为：

```text
t_min = max(F / P, Q / BW)
```

这里为什么用 max，而不是相加？因为模型允许搬运和计算同时进行。实际不能完全重叠时可能更慢；此外还有启动、同步、调度等成本。这是理论下界，不是保证达到的性能。

### 完整算一个例子

设一个操作有 200 GFLOPs，即 `200×10⁹` 次浮点操作；搬运 4 GB，即 `4×10⁹ bytes`。假设对应 dtype 的计算峰值是 100 TFLOP/s，HBM 带宽是 2 TB/s。

计算下界是 `200×10⁹ / 100×10¹² = 0.002 s = 2 ms`。访存下界也是 `4×10⁹ / 2×10¹² = 2 ms`，理想总下界为 2 ms。

现在减少一半计算，但数据量不变：计算下界变为 1 ms，访存仍是 2 ms，总下界仍是 2 ms。反过来只减少一半数据，计算仍限制在 2 ms。这个例子告诉你，优化要落在真正限制关键路径的资源上。

页面里的交互计算器正是这个模型。输入单位使用十进制 G/T；不要把第 3 课 KV 估算里的 GiB 直接当作 GB 而不做换算。

### 算术强度如何连接两本账

算术强度 I 定义为 `F/Q`，单位 FLOPs/byte，描述每搬运一个字节平均完成多少计算。上例 I=50 FLOPs/byte。

如果设备带宽是 BW，那么靠这份带宽能供给的计算速率上限约为 `BW×I`；同时它又不能超过算术峰值 P。因此：

```text
可达吞吐上限 ≤ min(P, BW × I)
```

在以算术强度为横轴、计算吞吐为纵轴的图上，左边是随 I 上升的斜线，右边是算术峰值的水平线，形状像屋顶，所以叫 Roofline。两段交汇的 I 为 `P/BW`。这帮助你判断，提高数据复用是否可能改变受限类型。

### 为什么 batch 会改变权重读取的收益

把一个 Linear 写成 `[M,K]×[K,N]`。M 可以理解成这次一起处理的 token 数。权重有 K×N 个元素，计算量约为 2MKN。若把权重读取近似看作主要流量，且 dtype 每元素 s bytes，那么相关算术强度大约随 `2M/s` 增长。

也就是说，M 增大时，同一份权重可以服务更多 token，计算增加得比这份权重读量快。这是 batch 可能改善效率的一种机制。

但这个推导故意忽略了输入输出、缓存命中、其他层与通信。后文会使用 kernel 这个词，指提交到 GPU 执行的计算程序；Python 中一个算子可能调用一个或多个 kernel。在长上下文 Attention 中，历史 KV 读取也很重要；在 MoE 中，不同专家收到的 token 数会改变矩阵形状；在高并发中，额外排队又可能伤害用户延迟。不能从这个局部公式推导“batch 越大越好”。

### Prefill 与 Decode 的直觉，必须保留条件

Prefill 同时处理较多位置，通常会出现较大的矩阵运算，更容易利用计算资源。单请求 Decode 每次只推进一个新位置，某些层可能更受权重读取或小算子开销影响。

“Prefill 计算受限、Decode 带宽受限”可以作为起始假设，但不是对所有模型、shape 和硬件都成立的定律。批量很大的 Decode、很短的 Prefill、量化转换、MoE 通信，以及 CPU 供给不足，都可能改变结论。

真正的流程是：根据形状推测资源需求 → 估算下界 → 用 profiler 验证。若实测与推测不符，先补充缺失的工作量或开销，而不是认为硬件必然出了问题。

### 读硬件数字时，先对齐四个条件

第一，精度格式是否一致：BF16 dense 计算不能代入 FP8 或 FP4 的宣传峰值。第二，是否使用特定稀疏性：需要满足相应稀疏结构才能使用那组数字。第三，单卡还是整机：多卡峰值相加不代表单个请求能用满。第四，峰值还是持续实测：实际 kernel 还受布局、大小、资源占用等限制。

此外，Q 应是相关层级的实际数据流量估算。重复执行时，某些数据可能命中片上缓存；用“所有权重每次都来自 HBM”的估算可能过大。相反，不连续访存与临时张量又可能产生额外流量。

因此一份负责任的估算要写出假设，而不是只留下一个小数点后两位的时间。

### 用反例检查你的推理

练习一：某算子理想计算 1 ms、访存 4 ms。计算峰值翻倍，模型下界是多少？仍是 4 ms。带宽翻倍呢？变为 2 ms。如果两者都翻倍，则变成 `max(0.5,2)=2 ms`，仍然受带宽限制。

练习二：Roofline 预测至少 2 ms，实测 5 ms，差的 3 ms 能否全部归因于网络？不能。这个差额可能来自非理想访存、启动、同步、资源限制，甚至工作量估错；要看时间线分解。

练习三：一个优化让某层 HBM 流量降低，但整机吞吐不变。至少提出两个解释。可以是该层并非关键瓶颈，或者节省的访存被新增转换/同步成本抵消。下一课会学习如何区分它们。
