### 这一课要把什么真正改出来

上一课的假设是：长 prefill 在一次调度中拿到过大工作块，可能让正在 decode 的短请求等待。我们现在把“限制工作块”翻译成一个可测试的策略，再说明怎样安全接入引擎。

这与直接在启动命令里改一个数字不同。你要定义新行为、保留原行为、处理边界，并证明代码运行到了你以为的位置。我们先在一个很小的函数里练习这些能力，随后才进入真实引擎。

本课附带的 `prefill_budget.py` 是教学策略，不是针对任意版本 vLLM 的可直接合入 patch。它让你先验证预算关系，避免第一次修改就同时面对大量模型与分布式复杂度。

### 先定义输入与不变量，再写 if

假设本轮共有 token_budget 个预算，其中 decode_tokens 已留给本轮 decode；某个 prefill 请求还剩 remaining 个 token。新增参数 cap 表示这个请求本次最多处理多少 token，cap=0 表示不启用新限制。

无论策略如何选择，至少应满足：分配非负，不超过 remaining，不超过剩余预算；若 cap>0，还不能超过 cap。若 decode 已用满预算，prefill 得到 0。出现非法负值则应明确报错，而不是隐式生成奇怪的负分配。

把这些条件先写出来，能防止你把“看起来简单的一行 min”写成改变资源约束的 bug。

### 一个可以完整看懂的策略函数

```python
def prefill_grant(remaining, token_budget, decode_tokens, cap=0):
    if min(remaining, token_budget, decode_tokens, cap) < 0:
        raise ValueError("counts must be non-negative")
    if decode_tokens > token_budget:
        raise ValueError("decode reservation exceeds budget")
    available = token_budget - decode_tokens
    limit = remaining if cap == 0 else cap
    return min(remaining, available, limit)
```

取 `remaining=2048,token_budget=512,decode_tokens=8`。默认 cap=0 时给 prefill 504 个 token；cap=128 时只给它 128 个。这里剩余的 376 个预算还可以由真实 scheduler 决定是否分给其他请求；这个函数不负责整个队列的分配。

这也揭示了模型的一个假设：decode 预算已经事先确定。在统一 token 调度、推测解码或某些模型路径中，decode 的分配不一定是“每请求固定 1 token”。接入时必须匹配实际执行语义，不能只根据本课变量名猜。

### 把测试写成能抓到错误的条件

先测关闭开关时与原公式一致，再测开启时不超预算。还要覆盖剩余不足 cap、预算为零、已经没有剩余工作、decode 已占满预算等边界。

例如下面几项可以手算：

```python
assert prefill_grant(2048, 512, 8, 0) == 504
assert prefill_grant(2048, 512, 8, 128) == 128
assert prefill_grant(7, 512, 8, 128) == 7
assert prefill_grant(2048, 8, 8, 128) == 0
```

如果开发者错误地把 available 写成 token_budget，第二项可能仍然通过，却会在“decode 已占满预算”时出错。这就是为什么不能只写默认参数的一项测试。

项目附带脚本会运行这些断言，并检查多组输入的不变量。它只能证明该函数的有限行为，不证明模型质量、缓存安全或真实服务性能。

### 接入真实引擎时，还缺哪几层工作

第一层是配置。找到引擎已有的参数解析和配置校验方式，新增字段时遵循项目规范，默认值保留原行为。避免只从临时环境变量里偷偷读取，导致实验难以追踪。

第二层是策略位置。在固定 commit 中找到“为请求决定本轮 token 数”的代码。要明确这里是否已经扣除了其他工作、是否考虑 KV 分配、是否允许 chunked prefill，以及后续模块是否能接收更小分配。

第三层是生命周期。不完整的 prefill 下一轮要从正确位置继续；取消与抢占后也不能重复计数。如果代码只改了本轮数字，却没有保持状态一致，就可能出现丢算、重算或卡死。

第四层是与执行后端的约束。某些路径涉及图执行、对齐、混合注意力或其他工作预算，新分配必须仍然满足它们。不能因为 toy 函数正确，就跳过这些接口检查。

### 先做观测 patch，证明你改到了正确位置

可以先只增加抽样统计：请求剩余 token、原计划分配、最终分配、预算、KV 申请结果、等待时间。用一个可控长请求确认这些值符合预期。

这一步也能发现“代码改了，运行的却是另一个安装包”或“配置没传到实际 scheduler”的问题。回到源码阅读课，重新核对 commit、包路径和运行环境。

观测必须控制开销。每 token 同步打印大量日志会改变时序，使你误以为策略本身造成退化。性能 A/B 时保留必要指标，关闭详细调试输出，并记录两组配置一致。

### 从函数测试走到系统回归

单位测试看预算关系。引擎集成测试要看请求最终是否完成、输出是否符合约定、取消是否释放资源、缓存不足时是否能恢复。模型测试则按改动性质比较 token、logits 或任务指标。

对于以保持模型计算为目标的调度改动，先在确定性/greedy 设置下比较默认和候选路径，缩小差异来源。不同 batch 与浮点实现可能带来差异，需要解释和合理容差；“输出看起来通顺”不是完整标准。

再用上一课的固定负载做交错 A/B。除了短请求尾延迟，还要看长请求 TTFT、总体吞吐、失败率和显存。若策略让某些请求长期没有进展，必须把公平性问题作为失败处理，而不是只报告短请求很快。

### 失败时应该怎样收缩问题

若发现输出不一致，先回到单请求、无并发、固定 seed/greedy 的最小输入。比较每轮分配和已处理位置，找出第一次偏离；再增加长短混合和取消路径。

若输出正确但性能没改善，检查实际分配与 trace 是否出现了预期变化。如果没有，可能是配置或调用链问题；如果变化存在却没有收益，则回到原假设，检查真正的关键路径。

这比继续叠加新优化更有效：每次只保留一项可解释的差异，让失败成为新的证据。

### 回退和交付不是最后补的一句话

你应能用一个明确配置恢复默认策略，并再次运行关键正确性与基线检查。代码层面也保留一个范围清楚的 patch，避免将无关重构、依赖升级和策略变化混在一起。

练习：如果 cap=0 被错误解释成“永远不处理 prefill”，会发生什么？新请求可能无法获得初始输出，默认配置就破坏兼容性。因此关闭开关测试必须是第一组，而不是最后补。
