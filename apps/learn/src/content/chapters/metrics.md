### 从“能回答”到“回答得好不好用”

前面三课解释了模型如何产生 token。但用户关心的是：点发送后多久开始输出，输出是否顺畅，系统忙时是否仍能完成请求。一个服务即使每次都返回 HTTP 200，也可能让人等待很久；反过来，一次 token/s 很高，也不说明它能稳定承载业务。

这一课先建立测量语言。后面所有优化都需要一份可以比较的基线；如果指标口径不清楚，就无法判断代码改动有没有收益。

我们用一个贯穿后续课程的场景：同一个服务同时处理短对话和长文档总结。短对话更关心及时开始和持续流畅，长文档会带来较长 prefill。暂时不要假设瓶颈一定在调度，先把时间线画出来。

### 一次请求的时间，并不只属于 GPU

设客户端在时刻 t0 发出请求，服务收到后可能做鉴权、解析、tokenization 和排队，之后引擎开始执行模型。第一个输出 token 经过服务端序列化、网络传输，到客户端的时刻是 t1。最后一个输出到达的时刻是 tend。

```text
客户端发送 → 网络/入口 → 排队 → Prefill → 首次采样 → 首 token 到达
                                              → 后续 Decode → 请求完成
```

客户端测到的 TTFT 是 `t1−t0`，不是单独的 prefill 时间。它包含沿路的等待。服务端内部也可能记录一个叫 TTFT 的指标，但起点可能是进入引擎或者离开队列。因此报告必须附“从哪个事件到哪个事件”，不要只写三个英文字母。

排查时，你可以把端到端时间当作用户体验，把内部阶段时间当作定位证据。二者互相补充，不能相互替代。如果服务端首 token 很快，客户端却很晚收到，优化 GPU kernel 未必能解决问题。

### 用一组时间戳算清指标

假设请求在 0 ms 发出，四个 token 分别在 200、230、265、300 ms 到达。则 TTFT=200 ms，总延迟=300 ms；相邻 token 的间隔 ITL 是 30、35、35 ms。

平均 TPOT 是 `(300−200)/(4−1)=33.33 ms/token`。分母是 3 个间隔，不是 4 个 token。只有一个输出 token 时没有 token 间隔，TPOT 应标为不可计算，而不是填 0。

如果你按总延迟计算 `4/0.3=13.33 token/s`，这包含首 token 前的等待；如果按后续生成阶段算 `3/0.1=30 token/s`，它不含等待。两者都可描述某个角度，但必须说明口径，不能用同一个名字混着比较。

真实流式接口常以 chunk 发送文本。一个 chunk 可能包含多个 token，甚至是空的控制事件。没有可靠 token 边界时，chunk 间隔只能叫 chunk 间隔，不能伪装成准确 ITL。

### 吞吐应该站在哪个窗口上看

服务输出吞吐可以定义为：同一个测量窗口内成功请求产生的总输出 token 数，除以窗口时长。假设 10 秒内成功产出 3000 token，就是 300 output token/s。

为什么不把每个请求的 token/s 相加？因为请求可能在不同时间开始结束，它们各自的分母不一致。要衡量整体容量，需要共同的时间窗口。

窗口也要讲清：是从第一条请求提交到最后一条完成，还是稳定运行中间的一段？预热算不算？失败请求的等待有没有计入窗口？本教材附带分析脚本使用你显式传入的整轮时长；成功输出计入分子，失败计入请求统计和整轮时间背景。

### 平均值为什么会掩盖难用的服务

假设 100 个请求里，99 个用时 1 秒，1 个用时 30 秒。平均是 1.29 秒，听起来可能不错，但总有人经历极端等待。分位数用来描述这个分布：P50 接近中位体验，P95/P99 观察尾部。

不同工具的分位数插值方法可能不同，小样本 P99 特别不稳定。十次请求中的“P99”不能自动代表生产中每百分之一请求的真实体验。比较前要记录样本量、失败率和重复轮次。

还有一个陷阱：如果超时请求从结果里被丢掉，剩下成功请求的延迟会显得更好。任何延迟改进都要同时检查失败、取消、截断和实际输出长度，避免把“少做了工作”误判为“做得更快”。

### 并发数与到达率不是同一个控制旋钮

闭环并发测试维持固定数量的在途请求：完成一个再发一个。它适合观察不同并发下的运行状态，但当服务变慢时，测试器自己也放慢了提交速度。

开放式到达率测试按计划时间发请求，例如每秒 5 条。若到达速度超过服务能力，队列会增长，延迟可能不断增加。这个模式更容易暴露过载，但需要记录客户端是否实际达到了计划速率。

例如服务变慢后，固定并发 8 的测试可能仍然稳定，只是每秒完成更少；固定到达率的测试则可能出现越来越长的等待。这不是结果矛盾，而是工作负载定义不同。

### 为贯穿案例设计第一份基线

先固定模型 revision、引擎 commit、硬件、量化、采样和输出上限，准备短 prompt 与长 prompt 两类数据。分别测低负载与较高负载，形成四格，再补一组长短混合流量。

每轮先预热，并明确 prefix cache 是冷还是热。不能让基线用冷缓存、候选用热缓存。负载生成应固定 seed 和到达序列，实际生成长度仍需记录；限制到相同 max_tokens 不保证每次实际输出一样长。

建议把一次实验目录看成一个可复现包：环境说明、启动命令、请求数据、逐请求日志、汇总表。先保存原始记录，再生成漂亮图表。至少重复三轮，若自然波动已很大，就先找不稳定来源，别急着优化。

### 运行分析器，并核对它没有替你猜数据

先运行 `python3 labs/analyze_benchmark.py --demo`。输出明确标注 `synthetic_demo=true`，这是口径演示，不是本机模型性能。实际输入 JSONL 的成功记录形如：

```json
{"id":"req-1","success":true,"ttft_ms":200,"latency_ms":300,"output_tokens":4}
```

失败记录至少包含唯一 id 和 `success:false`。读取真实日志后传入整轮测量秒数，例如 `--duration-s 120`。脚本拒绝负数、重复 ID、总延迟小于 TTFT 等不合理输入；但它无法替你验证 120 秒是否量得准确。

练习：如果候选版本输出吞吐提高 15%，同时成功率从 100% 降为 80%，是否合格？参考思路是先检查失败原因与完成工作量；在没有满足正确性和成功率门槛前，这不构成可接受的优化证据。
