### 计算预算还没用完，为什么请求仍在等待

上一课里我们按 token 预算安排工作，但真实引擎还有另一个条件：执行后产生的 K/V 必须有地方保存。若显存已经被活跃请求占满，即使 GPU 还有计算能力，调度器也不能无限接入新请求。

第三课估算了 KV 的元素数，这一课继续问“这些元素怎样管理”。同样的逻辑 token 数，分配方式、碎片和共享都可能改变实际可用容量。引擎优化不能只看公式里的总字节数。

### 为什么不为每个请求预留最大长度

假设配置最大上下文 32K，但大多数请求只用 1K。如果每个请求一进来就保留整段 32K 的连续缓存，会让大量空间闲置，压低并发容量。

另一种办法是随长度增长而扩容，但连续空间可能需要搬移，多个长短序列也会制造分配难题。分页思想把一个逻辑序列拆成固定大小的块，再把逻辑块映射到分散的物理块。

逻辑序列仍按 token 顺序读取，但物理内存不要求整段连续。Attention kernel 通过块表找到需要的数据。类似操作系统分页的比喻可以帮助理解，但不要假设它就是直接使用 CPU 虚拟内存的全部机制。

### 手工走一次块分配

设每块装 16 个 token。长度 15 的序列需要 1 块，长度 16 仍是 1 块，增加到 17 时需要第 2 块，长度 33 则需要 3 块。

```text
逻辑 token 0..15   → 逻辑块0 → 物理块7
逻辑 token 16..31  → 逻辑块1 → 物理块2
逻辑 token 32     → 逻辑块2 → 物理块11
```

物理块顺序可以是 7、2、11，逻辑顺序不变。第 33 个 token 让第三块只用掉一个位置，余下 15 个位置是尾块内部空闲。它不等于内存泄漏：这是当前分配粒度带来的浪费。

若每 token 需要 128 KiB，逻辑 33 token 是 4.125 MiB，按 48-token 容量分配则是 6 MiB，差额 1.875 MiB。这里仍只算缓存主体，没有包括块表、对齐和其他开销。

### 块越小，真的越好吗

更小的块可以减少尾块空闲，但块表变长、管理次数增加，访问和 kernel 的组织也可能更复杂。块大小还是底层实现的约束，不能只改 Python 常量而忽略 kernel 支持。

这是系统工程中反复出现的权衡：更细的粒度减少某类浪费，却可能增加另一类开销。调度 chunk 与 KV block 也不是同一个概念；一个描述本轮计算多少 token，另一个描述缓存如何分配。

### 共享前缀时，谁拥有这块内存

假设两个请求开头完全相同，且满足模型、位置与其他匹配条件，那么已计算的前缀 KV 可能被共享。这样既减少重复 prefill，也可能节约缓存。

但共享后，一个请求结束不能直接释放仍被另一个请求引用的块。实现需要引用计数或等价的所有权机制。若一个共享的未满块要被不同请求继续写入，还需要正确处理可变部分，不能让两个分支互相覆盖。

另一个区分是“可复用但无人正在用的缓存块”和“仍被活跃请求依赖的块”。前者可能被驱逐来腾空间；后者通常不能随意覆盖。不同实现的缓存淘汰与共享粒度不同，必须读固定版本。

### 为什么相似文本不能直接共享 KV

KV 是模型对具体输入及其位置的数值结果。即使两段文本语义相似，只要 token 序列不同，通常也不能假定 KV 相同。模型权重、adapter、位置处理或相关配置变化，也会影响结果。

因此 prefix caching 是满足确定匹配条件的计算复用，不是向量数据库的相似搜索。只比较字符串开头，或者只比较 token ID 而忽略其他影响条件，都可能导致错误复用。

实验时还要记录冷热状态。候选配置恰好命中了前缀，而基线没有命中，就会让你误以为 scheduler patch 加速了 prefill。

### 内存不足时，引擎需要做选择

可选行为取决于实现：等待更多资源、驱逐可回收缓存、抢占某些请求并之后重算，或者使用额外的 offload 机制。不要假设所有版本都通过 CPU swapping 解决不足。

抢占意味着已经运行的请求可能暂时停止前进，之后还要付出恢复或重算成本。因此它影响的不只是显存曲线，还会影响请求尾延迟。

在源码地图上，应找到 Scheduler 与 KV 管理器的接口：申请可能失败吗？失败后会保留哪些状态？取消时是否幂等释放（重复处理同一次取消，不会再次扣减引用或重复回收）？如果你的新策略提前安排更多 token，就必须保证它没有绕过这些约束。

### 用小容量，迫使错误显现

普通大显存测试可能很难触发边界。为验证缓存改动，可以在独立实验环境使用很小的缓存池，让以下路径反复发生：跨块增长、共享后某一请求结束、运行中取消、空间耗尽后重试。

每一步记录已分配块、可回收块、引用关系和请求输出，检查没有丢 token、重复输出或悬空引用。不要只看“显存下降了”就宣布成功；提前释放仍在使用的块，同样可能让显存下降。

练习：两个请求共享两个完整块，其中一个结束，另一个仍在运行。共享块能立即释放吗？不能，只能减少相应引用，直到没有依赖或满足安全回收条件。再问：长度 33、块大小 16 的序列，如果删除最后一个 token，是否一定马上归还整块？这取决于实现何时更新状态与回收，不能只从逻辑长度推断真实回收时刻。

### 从缓存管理走向算子实现

你现在应该能把逻辑序列、块表、物理存储与请求生命周期放在同一张图里。分页缓存要求 kernel 按相应布局读取数据，因此引擎层与算子层并不是两套互不相关的知识。

本阶段的基础交付是职责地图、调度实验设计与缓存生命周期草图。真实引擎上的观测属于进阶练习；新策略的实现和回归将在第 17 课集中完成。不要因为尚未写出策略 patch 就认为这三课没有学会。
