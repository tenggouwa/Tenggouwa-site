### 数学相同，为什么实现速度不同

前面已经看到，模型层最终会调用矩阵乘法、归一化和 Attention 等操作。把它们翻译成 GPU 程序时，除了算什么，还要决定谁算、数据放哪里、读取顺序怎样安排。

这一课先建立执行和内存的基本模型。你不必立即写出比成熟库更快的 kernel，但需要能解释一次实验为什么快或慢。否则调整 block size 只是换了一组更底层的参数继续碰运气。

### 从 CPU 循环到大量并行工作

在 CPU 上做向量加法，你可能写 `for i in range(N): y[i]=a[i]+b[i]`。GPU 常把许多 i 分配给不同线程，同时推进。

CUDA 用 thread、block、grid 组织这些工作。一个 block 里的线程可以通过共享内存与同步协作；多个 block 组成一次 kernel launch 的 grid，分配到 GPU 的多个 SM 上执行。SM 可以理解成能够运行多组线程的计算单元。

NVIDIA GPU 常以 32 个线程组成 warp 来调度相关指令。SIMT 允许线程拥有各自的数据和控制路径，但同一 warp 出现分支差异时，可能降低有效执行效率。这里的重点是理解工作分组；更具体的行为要对照目标架构。

Triton 提供较高层的表达方式：一个 program 操作一块张量，编译器负责将它映射到线程和指令。Triton 的 block 张量不是 CUDA thread block 的逐字替代物，变量名相似并不代表执行细节相同。

### 三类存储各自解决什么问题

HBM 提供较大的设备内存，模型权重和 KV 主体通常在这里，但读取成本相对较高。寄存器保存线程计算中的局部值，访问快，却数量有限。Shared memory 是 SM 上可供线程块协作使用的显式存储，也有限。

GPU 还有缓存层，它会影响哪些读取真正到达 HBM。你不能把每个源代码里的 load 都简单算成一次完整 HBM 访问，但仍可以从数据流量建立初始估算，再用指标校验。

优化经常是在“减少重复远端读取”和“不要耗尽片上资源”之间找平衡。把所有东西都留在寄存器里并不现实；过多寄存器需求可能降低驻留工作量，甚至导致 spill 到更慢的存储。

### 连续地址为什么经常更友好

假设一个 warp 的线程分别读取连续的 FP32 元素，所需地址通常可以被组织成较少的内存事务。若每个线程跨很大步长读取，可能触及更多内存段，搬运许多用不到的数据。

这就是合并访存的直觉。真正的事务数量还受地址对齐、元素大小和访问分布影响，不能仅凭“连续”两个字计算精确速度。[CUDA 官方执行与访存说明](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)可作为进一步阅读。

前面学过 transpose 往往改变 stride。Stride 指某一维索引加一时，底层存储需要跨过多少个元素；contiguous 指元素按相应连续布局保存。现在可以理解：逻辑 shape 看起来相同的两个张量，底层地址访问模式可能不同。某个 kernel 对 contiguous 输入很快，不代表对任意 stride 都一样快。

### 用 1000 个元素理解尾部 mask

设每个 Triton program 处理 256 个元素。1000 个元素需要 `ceil(1000/256)=4` 个 program。前三个分别处理 0..255、256..511、512..767，最后一个逻辑上处理 768..1023，但 1000..1023 已经越界。

因此需要 `offsets < N` 的 mask：只读取和写入有效位置。这个检查不是可有可无的性能选项，而是正确性的一部分。测试长度 1024 可能看不出问题，所以要专门测 1000、1025 等非整除形状。

用伪代码表示：

```text
start = program_id × BLOCK
indices = start + [0, 1, ..., BLOCK-1]
valid = indices < N
加载 a[indices]、b[indices]，只允许 valid 位置
计算相加
写回 y[indices]，只允许 valid 位置
```

先确认每个输出位置恰好写一次，再讨论哪个 BLOCK 更快。越界不一定立即导致报错，可能污染别的数据或只在某些输入上出现。

### Tiling 如何增加数据复用

矩阵乘法中，一个 A 元素会参与多个输出，一个 B 元素也会被多个输出使用。若每次乘加都重新从 HBM 读取它们，会浪费带宽。

Tiling 把输出分成小块，将相关的 A/B 子块加载到更快的存储中，复用后再推进到下一块。它提高算术强度，使更多计算对应到同一次数据搬运。这与 Roofline 课里“提高 FLOPs/byte”的目标对应起来。

但是 tile 太大会消耗更多寄存器或 shared memory，可能减少同时可运行的 block。小 tile 则可能复用不足。不存在对所有 shape、dtype 和 GPU 都最好的单一配置。

### Occupancy 为什么不是最终目标

在这里讨论的 CUDA SM 层面，occupancy 通常指活跃 warp 数相对该 SM 可支持最大活跃 warp 数的比例，用来辅助分析延迟隐藏。它不是显存使用率，也不是 GPU utilization；定义可对照 [NVIDIA Occupancy 说明](https://developer.nvidia.com/blog/cuda-pro-tip-occupancy-api-simplifies-launch-configuration/)。它高，不代表所有线程都在做有价值的工作；它低，也不意味着性能一定差，某些高复用 kernel 在较低 occupancy 下仍然高效。

你的目标是缩短正确计算的关键路径，而不是把一个资源指标填满。指标需要与有效吞吐、数据流量和具体限制一起看。

做实验时改变一个 tile 或 num_warps 参数，先验证输出，再观察时间与资源指标。若速度下降，尝试解释是访存、寄存器、并行度还是启动成本变化，而不是只挑最快的数字记下来。

### 本课该怎样练习

先完成 Triton 官方向量加法，测试 1、1000、1024、1025 个元素。改变 BLOCK，检查尾部是否正确，记录哪些配置更慢。没有 NVIDIA 实验机时，先手算索引和 mask，等环境具备后再填实测结果。

思考题：让每个线程做更多工作，为什么既可能变快也可能变慢？参考思路是增加局部复用、减少部分开销可能有利，但过多寄存器和更少并行工作可能不利。答案必须包含这两种方向。

下一课会把这些概念用于 Softmax：将多次读写融合在一起，观察减少数据搬运如何转化为某些形状上的收益，以及为什么它不保证在所有形状都赢。
