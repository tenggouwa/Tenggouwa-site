### 为什么每生成一个 token，不应该重算整个故事

上一课我们算清了 Attention：新输出来自 query 对允许读取的 keys 和 values 的加权汇总。现在假设用户输入四个 token，模型预测出第五个。要继续预测第六个，最直观的办法是把五个 token 全部再过一遍网络。

这个办法容易实现，却重复了很多工作。对于标准 causal Transformer，前四个位置看不到第五个位置，它们在各层已经算出的状态不会因为后文出现而变化。如果模型权重、位置、mask 等条件不变，这些历史位置的 K/V 就可以继续使用。

本课要把“可以缓存”讲清楚，也把“缓存没有省掉什么”讲清楚。否则你以后看到长上下文变慢，很容易误以为缓存失效了。

### Prefill 与 Decode 的时间顺序

先看一个含三个输入 token 的请求。Prefill 处理这三个输入，建立各层初始缓存，并根据最后位置的输出预测第一个生成 token。随后把刚生成的 token 喂回模型，做一次增量计算，预测下一个 token；如此反复。

用位置编号表示：

```text
Prefill: 输入位置 0,1,2 → 建立 3 个位置的 KV → 预测位置 3
Decode:  输入位置 3   → KV 增长到 4         → 预测位置 4
Decode:  输入位置 4   → KV 增长到 5         → 预测位置 5
```

注意一个容易错一位的细节：某个 token 刚被采样出来时，不代表它自己的 KV 已经写入所有层；通常要在下一次把它作为输入执行时，才会产生对应 KV。具体引擎可能流水化这几个步骤，所以统计缓存长度时要看计时位置。

### 每一层究竟留下什么

在单层中，新 token 产生 `q_new、k_new、v_new`。把新 K/V 接在历史缓存后面，新 Q 与全部合法的 K 做匹配，再读取 V。只需输出新位置的结果，不必再次输出所有旧位置。

典型多层模型不是只有一份全局 K/V。每层的输入状态不同、投影权重不同，因此要有各层自己的缓存。也不能把第二层的 K/V 拿给第一层使用。

新的 Q 通常不需要长期保存：下一步会有另一个新 Q，而标准 attention 不通过旧 Q 检索历史。历史 K/V 则仍然是未来 query 的读取对象。因此工程里常说 KV Cache，而不是 QKV Cache。

缓存有效还有条件：同一模型/adapter、相同前缀和位置语义、相同相关计算配置。它不是“上次见过类似文本就可以复用”。跨请求的 prefix cache 必须满足对应实现的匹配条件，之后的缓存管理课会继续展开。

### 用一个四位置例子对齐两条路径

设我们已经准备好四个位置的 Q/K/V。完整计算对每个 query 使用 causal mask；增量计算每次只把当前 K/V 追加进去。第四步的两条路径都应计算“位置 3 的 Q 读取位置 0..3 的 K/V”。

下载的 `attention_reference.py` 把两条路径写成 `full_attention` 和 `cached_attention`。它使用 Python 标准库，不需要 GPU 或训练权重。先运行：

```bash
python3 labs/attention_reference.py --tokens 16 --dim 8 --seed 7
```

输出里的 `max_abs_error` 是两条路径所有位置的最大差异，`causal_error` 检查修改最后位置的 K/V 是否影响更早输出。对于这个共享基础运算的教学实现，两项应接近 0。它证明的是这个最小实现的等价性，不是任何真实模型服务都已经正确。

更强的验证是写一个独立的向量化参考实现，用 `softmax(QKᵀ/√d + mask)V` 计算整段输出，再与逐位置结果比较。先固定 FP64 做机制校验，再在较低精度下使用合理容差。浮点顺序不同可能导致很小的差异，不要强制所有后端逐 bit 相同。

### 一个常见实现陷阱：新 query 在矩形矩阵的哪里

Prefill 中 Q/K 长度相同，标准下三角 mask 很直观。Decode 可能只有 1 个 query，却有 100 个 key。这时 `[1,100]` 分数矩阵中的唯一一行，代表的是最后一个位置，而不是位置 0。

如果你机械套一个“左上角对齐”的下三角 mask，它可能只允许读第一个 key，结果就错了。对于只含一个新 token 且缓存没有未来项的普通 decode，它应读取全部已有合法 K/V。分块增量输入则要用“历史长度 + 块内位置”决定可见范围。

使用库函数时必须读其非方阵 causal mask 的定义，而不能只看到 `is_causal=True` 就认为适合所有缓存场景。PyTorch 对这一点有明确说明：[SDPA 接口文档](https://docs.pytorch.org/docs/main/generated/torch.nn.functional.scaled_dot_product_attention.html)。

### 从元素数推导 KV 显存

标准 MHA/GQA 中，假设所有层配置相同、K/V 的 head_dim 相同，每个 token 在一层要保存两份张量：每份有 `Hkv×d` 个元素。若共有 L 层，每元素 s bytes，总共 N 个缓存 token，就得到：

```text
KV bytes = 2 × L × N × Hkv × d × s
```

逐项解释：2 是 K 与 V；L 是层数；N 是所有请求缓存长度的总和；Hkv 是 KV 头数；d 是每头维度；s 由缓存 dtype 决定。别把 query 头数无条件代替 KV 头数。

取 `L=32,Hkv=8,d=128,s=2`，每 token 是 `2×32×8×128×2=131072 bytes=128 KiB`。一个 8192-token 请求约为 1 GiB；四个同长度请求约 4 GiB。这里 GiB 按 `2³⁰ bytes` 计算，不是十进制 GB。

MHA 中每个 query head 有对应 KV head；GQA 中多个 query head 共享 KV head，因而可以减少缓存量。MLA 使用压缩 latent 等特定缓存形式，不能直接套本公式。多卡分片、复制、滑窗、混合层、量化 scale 和分页碎片，也都要另行计算。

### KV Cache 没有消灭长上下文的成本

旧 token 的投影和部分层计算被省下了，但新 query 仍然需要读取历史 keys/values。标准全注意力下，读取的历史越长，相关访存与计算通常越多。缓存既节约重算，也占用不断增长的显存，这是它的基本交换条件。

此外，服务的最大上下文配置不是“每个请求此刻都占满这么多 KV”。实际占用还与在途请求、已处理 token、缓存块分配和实现策略相关。因此看容量时要分清：配置上限、预留池大小、当前使用量、逻辑 token 数。

### 练习、参考思路与下一步

先自己算：同样的模型，KV heads 从 8 降到 4，其他条件不变，一个 8192-token 请求需要多少主体缓存？答案是 0.5 GiB，因为公式对 Hkv 线性。若上下文翻倍，同时请求数也翻倍，总缓存会变为原来的四倍。

再解释：为什么给模型增加缓存不能保证所有负载都更快？参考思路是区分重复计算、历史读取、缓存分配成本，以及小任务中的固定开销。机制正确与服务性能良好是两件需要分别验证的事。
