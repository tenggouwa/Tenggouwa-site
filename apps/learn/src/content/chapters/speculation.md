### 一步一个 token 的依赖，能怎样缓解

我们一直把 decode 理解为：执行目标模型，预测一个 token，再把它喂回去。这个依赖很难直接并行展开，因为后一步的输入还没确定。

推测解码尝试先用较便宜的方法提出多个候选，再由目标模型验证。如果一段候选恰好符合验证条件，就可能一次前进多个 token，减少重复执行昂贵目标步骤的轮数。

MTP 是 Multi-Token Prediction（多 token 预测），例如借助模型的辅助预测模块提供后续位置候选。推测解码也可以使用独立的小模型等候选来源，并非都属于 MTP。MTP 可以提供多个候选，但“能预测多个 token”与“完整、正确、有效的推测解码”不是同一件事。后者还包括验证、接受、拒绝修正、缓存管理和调度。本课把这几部分拆开。

### 先用 greedy 例子理解接受前缀

假设候选方法提出 `[A,B,C]`。目标模型在正确的自回归前缀下依次最偏好 A、B、D，那么前两项可以接受，第三项不一致，需要按目标路径处理这一位置。

为什么不能继续接受 C 之后的候选？因为那些候选是基于包含 C 的假设前缀产生的，而 C 已被拒绝。后续上下文变了，不能把原来预测结果直接接上。

这说明接受的一般是一个连续前缀，而不是从候选列表中随意挑几个看起来对的 token。它也解释了缓存为什么需要区分已确认前缀和暂存候选状态。

### 为什么候选验证有机会更便宜

给定一串候选，目标模型可以把相关位置组织成一次批量前向，像小段 prefill 一样利用更多并行计算，而不是完整串行调用多次目标模型。

但验证 k 个候选并不等于只付一次普通 token 的成本。输入形状、历史长度、batch 和 kernel 都会影响验证时间，候选方法自身也要计算。推测解码能否赢，取决于额外花费与实际前进量的关系。

在低负载、某些带宽受限场景里，额外计算可能更容易被摊薄；高负载时，原本的 batching 已较高效，验证额外候选反而可能挤占资源。因此至少分别看低负载延迟和高负载吞吐。

### 随机采样为什么不能只做“选项相同”比较

Greedy 总选最高分 token，容易定义逐步匹配。Sampling 从概率分布取样，候选模型与目标模型的概率可能不同，简单接受“目标也可能生成”的候选会改变分布。

经典精确 speculative sampling 会结合目标概率 p 与候选概率 q 使用相应接受概率，例如某些算法中的 `min(1,p(x)/q(x))`，拒绝后还需要从修正分布采样。只有接受与修正机制完整且满足算法假设，才能讨论保持目标分布。

这段说明不是让你直接把公式贴到任何 MTP 实现里。不同候选结构、树验证或辅助头有不同条件；需要对照使用的具体算法。也不能要求两个随机执行路径在同一个 seed 下必然输出逐字相同，随机数消费顺序可能不同。

### 用期望值建立收益账本

页面用一个刻意简化的模型：k 个候选，每个位置在前面已接受的条件下，接受概率都为 a；实现每轮还能产出一个额外 token。前进至少第二个 token 的概率为 a，至少第三个为 a²，以此类推。

于是期望前进量为：

```text
E = 1 + a + a² + … + aᵏ
```

这个“1”来自模型假设的每轮额外 token，不是所有实现无条件满足的事实。若你的引擎不符合这个流程，就要换成实际统计的每轮前进量。

设普通 decode 成本 t，候选成本 D，验证成本 V，忽略其他开销，理论加速约为 `E×t/(D+V)`。只有分子增长超过新增成本，推测才有收益。

### 完整算一笔账，再看反例

取 k=4、a=0.8，E 为 `1+0.8+0.64+0.512+0.4096=3.3616`。若 t=10 ms，D=3 ms，V=12 ms，那么一轮 15 ms 平均前进约 3.36 token，加速比约 2.24。

现在保持接受概率不变，把验证时间增到 35 ms，总成本变成 38 ms，加速比约 `33.616/38=0.885`，反而减速。接受率没变，性能却改变了方向。

若 a=0，每轮只能前进简化模型中的一个 token，却仍付出候选和验证成本，通常更容易亏损。这也是为什么“成功启用 MTP”不等于“当前负载一定加速”。

### 更长的候选，为什么不是免费收益

假设 a=0.8，把 k 从 4 增到 8，新增位置的贡献是 a⁵、a⁶、a⁷、a⁸，越来越小；候选和验证成本却可能继续增加。较后候选还可能在更困难的上下文中接受得更少，因此实际每位置条件概率也未必相同。

真实 batch 里不同请求接受长度不同，这会影响后续组织和缓存回收。页面提供独立的 D/V 滑块，是为了让你探索收益条件，不是声称 D/V 与 k 无关。

### 在引擎里应该记录什么

至少记录每轮提出多少候选、接受多少、实际前进多少 token、候选时间、验证时间和相关显存。还要说明请求负载、输入/输出长度、温度等采样条件。

正确性方面，greedy 可与无推测路径比较 token 序列，并进一步定位 logits 差异；sampling 则需要依据算法讨论分布与统计验证。停止 token、输出长度上限、取消、候选拒绝后的 KV 回收也都是边界。

只看接受率百分比不足以确定收益。接受率的分母也要说明：按候选 token 计，还是按每轮成功长度计？不同统计名字相近，含义却可能不同。

### 从参数试验走向定制策略

一个适合你的入门实验是固定其余条件，只改变候选长度，分别测低负载和高负载，保存每轮前进量与成本。如果找到稳定规律，再考虑根据负载或接受情况动态调整，而不是直接把某个 k 写死为“最优”。

练习：接受率从 70% 升到 85%，能否只凭这一项判断候选模型更适合？不能，还需要候选耗时、验证形状和真实前进量。更准确但更昂贵的候选可能让总系统变慢。
