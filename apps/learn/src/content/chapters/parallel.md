### 多一张 GPU，增加的不只有算力

现在模型能在单卡上运行，你希望用更多卡提高容量或速度。启动参数里可以设置 DP、TP，有时还有 PP。但它们分的不是同一种东西：有的分请求，有的分一层里的计算，有的分模型层。

这一课先不背参数组合。我们用一个小矩阵明确“每张卡持有什么数据、计算什么、需要和谁交换什么”。理解这个映射后，再读实际引擎的并行配置。

本课先讨论普通 dense 模型。MoE 的 DP+EP 组合会改变权重布局，下一课再加上这层复杂度。

### DP：多份模型，处理不同请求

普通推理 Data Parallel 可以理解为多个模型副本各自接收请求。若两张卡都能放下整个模型，GPU0 处理请求 A，GPU1 处理请求 B。副本之间不必为 A 的每一层都同步中间结果。

它通常能提高整体服务吞吐，但不会自动让单个请求的模型计算快一倍。它还复制权重，占用更多总显存。入口需要把请求分配到各副本，负载均衡和 prefix cache 命中也会影响实际收益。

所以“DP=2”首先是请求分工与副本布局的问题。若用户只发一个请求，另一副本可能空闲；若路由把长请求集中到某一副本，也会发生负载不均。

### TP：让多卡共同完成一层计算

设 `Y=XW`，X 为 `[M,K]`，W 为 `[K,N]`。一种切法是沿输出维 N 把 W 分成左右两半，每张卡得到一部分输出列。数学上：

```text
W = [W0 | W1]
Y0 = XW0
Y1 = XW1
Y = [Y0 | Y1]
```

如果下一层能继续使用分片布局，不一定马上把 Y 拼起来；如果需要完整输出，就要进行相应的数据收集。通信在哪里发生，要结合前后层，而不是看到分片就一律加一次 all-gather。

另一种切法是沿输入维 K，把 X 和 W 对应分开。这时每张卡算的是完整输出的部分和：`Y=X0W0+X1W1`。要得到完整 Y，需要把部分和合并，常见工具是 all-reduce 或相关 collective 组合。

### 用数字区别“拼接”和“求和”

取 `x=[1,2]`，`W=[[1,3],[2,4]]`。完整结果是 `[5,11]`。

沿输出列分：第一张卡持有 `[1,2]ᵀ`，算出 5；第二张卡持有 `[3,4]ᵀ`，算出 11。最终是拼接 `[5,11]`。

沿输入行分：第一张卡算 `1×[1,3]=[1,3]`，第二张卡算 `2×[2,4]=[4,8]`。最终把对应元素相加，得到 `[5,11]`。

这两种分片都正确，但中间数据形状和通信语义不同。阅读一个并行 Linear 时，先找它沿哪一维切，再看输入是否已经分片、输出希望保持什么布局。

### All-reduce、All-gather 与 All-to-all

All-reduce 把各 rank 的对应数据做归约，并让参与者得到归约结果；All-gather 收集各 rank 的不同分片；All-to-all 则让每个 rank 向其他 rank 交换各自不同的数据部分。

Rank 是分布式进程在某个进程组中的身份。一个设备/进程可能参与不同的逻辑组，例如 TP group 和 DP group。只看到 rank=0 并不足以判断它在整机中的全部职责，还要看所属 group。

别把“通信”当成一个均匀常数。消息大小、拓扑、算法、同步依赖和其他设备到达时间，都会影响耗时。

### 为什么通信会抵消算力收益

一个粗略模型是 `t_comm≈α+bytes/BW`。α 是固定延迟，BW 是有效传输带宽。小消息主要受固定延迟影响，大消息更可能受带宽影响。这不是对所有 collective 的精确公式，但适合形成初始直觉。

若每层单卡计算 1 ms，拆到两卡后计算变成 0.6 ms，却增加 0.5 ms 无法隐藏的通信，那整体可能变慢。另一方面，如果单卡放不下模型，多卡分片首先解决的是可运行性，不一定以单请求加速为唯一目标。

通信与计算可以通过合适的依赖和调度重叠，但“启用 overlap”不代表通信从账本中消失。需要 trace 证明它是否在关键路径外，以及有没有争用计算或内存资源。

### PP 又为什么需要流水

Pipeline Parallel 把不同层放到不同设备。请求必须按层依赖前进；单个 microbatch 经过前一阶段后，后一阶段才能处理相应数据。

Microbatch 是拆出来的一小组输入工作。多个 microbatch 可以形成流水，但启动、结束和负载不均会产生气泡。分层越不均衡，较快阶段等待越多。PP 可以分摊权重容量，但对交互式自回归解码的延迟与调度也有额外挑战。

本课不要求你立即实现 PP，只要知道它与 TP、DP 解决的问题不同。不要用“多卡并行”四个字省略实际切分方式。

### 做一份可解释的并行实验

记录每个 rank 的权重分片、输入分片、输出布局、通信点、GPU 拓扑和引擎版本。先验证单卡与多卡输出在约定条件下相符，再测不同 batch 和输入长度。

比较时同时关注每请求延迟、整体吞吐、单卡/总显存和通信时间。多卡后吞吐提高但每请求成本增加，并不自动代表更优；要回到你最初的容量或体验目标。

练习：如果两张卡以 DP 部署，单请求没有变快，这是否说明 DP 失效？不是，它主要分担不同请求。再问：TP 中某个 collective 很长，是否一定是网络慢？也可能有 rank 更晚完成计算，其他 rank 在同步等待它。
