### 为什么 MoE 不能只看激活参数量

你部署 MoE 模型时，常会看到很大的总参数量和较小的每 token 激活参数量。直觉上似乎只算一小部分，应该很省。但实际运行还需要保存或调入专家权重、路由 token、交换数据，并处理负载不均。

这一课把一个 MoE 层拆成可观察的阶段。我们暂时采用“router 选 top-k 专家、专家执行 MLP、结果加权合并”的教学结构；实际模型可能有共享专家、不同门控与归一化方式，必须对照模型定义。

### 从一个 token 开始走完整条链

输入 token 的隐藏向量先进入 router，得到对各专家的分数。选择 top-k 后，该 token 会被发送到对应专家。专家是可学习的子网络，不是根据人类标签手工写出的“数学专家”或“代码专家”。

每个被选中的专家产生一个输出向量，随后按路由权重组合回该 token 的结果。这里有两个需要区分的动作：选择哪些专家，以及给选中输出多大权重。不同模型对分数、偏置和归一化的处理可能不同。

假设 token A 选择专家 0、3，权重为 0.7、0.3，专家输出分别为 `[2,1]`、`[0,5]`，那么合并结果是 `[1.4,2.2]`。这只是手算示意，不代表某个真实模型的固定 gate 规则。

### 从一个 token 到一批 token

专家通常希望把分配给自己的多个 token 整理成批量矩阵运算。如果 100 个原始 token 每个选 top-2，就有 200 条专家分配；同一个 token 参与两次专家计算，结果稍后汇回。

这些分配可能很不均匀。假设有 8 个被路由的专家，200 条分配平均每专家 25 个 token，但不代表实际都是 25。有的专家可能空，有的接收大量 token。矩阵形状变化会影响 kernel 效率，所以即使总激活参数量相似，执行时间也可能不同。

这解释了为什么 MoE 性能分析需要看路由后的 token 分布，而不只看进入模型的 batch size。

### EP 把专家放到不同设备

Expert Parallel 将专家分布到不同 GPU/rank。原始 token 所在设备不一定拥有被选中的专家，因此需要 dispatch 把相应隐藏状态送过去；专家计算完，再 combine 把结果送回或按实现组织合并。

概念链是：

```text
router → 按专家/目标 rank 整理 token → dispatch
       → 专家 MLP → combine → 恢复原 token 顺序并加权
```

其中的数据交换常涉及 all-to-all 类通信。但实际 backend、打包格式、跨机/机内分层以及计算通信重叠都可能不同，不能只凭 EP 开关推断具体实现。

### 一个四卡偏斜例子

设四个 rank 在这一层收到的专家 token 数为 `[100,100,100,400]`。总数是 700，平均 175，但同步阶段的关键路径可能接近最忙 rank，而不是平均值。

若近似每个专家 token 的计算成本一致，最忙 rank 的负载约是平均的 2.29 倍。其余 rank 可能更早算完，却仍要等待合并。这还只是简化模型；专家矩阵形状、共享专家和通信也会改变实际时间。

因此一张“全机平均 GPU 利用率”的图可能隐藏严重偏斜。你需要按 rank、按专家统计分配数和执行时间，再检查二者是否与尾延迟相关。

### 负载均衡为什么也有成本

引擎可能通过改变专家映射或使用冗余专家副本来改善负载。这样做可能消耗额外显存、迁移权重并引入协调成本。负载随请求变化，上一分钟的热门专家也不一定永远热门。

不能仅看到均衡后柱状图更平就宣布成功。还要看重分配成本、端到端吞吐和延迟，以及稳定性。一个策略如果为追逐短期噪声不断迁移，也可能得不偿失。

在 DP+EP 组合中，还要看 attention 层和专家层分别如何复制/分片。不能把“DP=4”直接理解为四张卡各有完整 MoE 模型。画出每个 rank 持有的权重，是读配置的第一步。

### 你的第一个定制工作，应从观测开始

先把一层的时间分为 router、dispatch、expert compute、combine。再记录每专家分配量、每 rank 计算量与到达 collective 的时间。

如果通信区间长，可能是传输慢，也可能是某个 rank 到达得晚。先通过时间线区分。如果偏斜稳定存在并进入关键路径，再选择布局或均衡策略做 A/B。

保留默认路径，使用固定模型、输入到达序列、拓扑和 backend。先只改一项，避免把路由规则、专家布局、量化和通信库同时改变而无法归因。

### 正确性比“收到相同数量”更严格

Token dispatch 会改变排列，combine 必须恢复相应关系。总数一致仍可能把 A 的专家输出加给 B。还要验证 top-k 权重、重复分配、空专家、极端偏斜，以及跨 rank 输出顺序。

一个可手算的小例子很有价值：用带标签的 toy token、已知专家输出与固定门控，确认每项返回给正确位置。再扩展到随机测试和真实模型，而不是直接从大模型的一段通顺文本判断成功。

练习：100 token、top-2 路由产生 200 条分配，它们是否意味着输入 batch 变成了 200 个用户请求？不是，这是同一批 token 在专家层的工作副本。另一个问题：改变专家物理映射应否改变逻辑路由结果？如果目标只是执行优化，不应无意改变模型语义。

下一课讨论 MTP 与推测解码。它同样需要同时计算收益和额外成本，不过这次被改变的是每轮向前推进多少 token，以及为此付出的候选与验证计算。
