### 前面学了很多机制，现在只选择一个问题

到这里，你已经接触了 Attention、KV、调度、kernel、并行和推测解码。但真正的工程项目不会因为你把所有技术都用一遍就成功。它需要围绕一个具体问题，建立从现象到原因、从原因到改动的证据链。

最后三课继续使用长文档与短对话混跑的案例。我们会先写实验提案，下一课实现一个有清楚边界的小策略，最后形成报告。这里的数字和策略示例都是教学用途，不代表你的真实部署已经存在同样瓶颈。

### 先把抱怨改写为可测量的问题

“模型很慢”无法直接指导工作。把它改成：“在固定的长短请求混合到达序列下，短对话的逐 token 间隔出现长尾，超过我们预先约定的体验目标。”

这句话限定了工作负载、受影响对象、指标和目标。再补上模型版本、引擎 commit、硬件、缓存条件，就形成一个可复现的实验起点。

先确认指标确实反映用户问题。若测到的是 chunk 间隔，不要写成精确 ITL；若请求卡在入口队列，不要把它归到模型 token 生成阶段。定义错误会把你带到错误代码层。

### 把观察、解释和方案分开写

观察是证据直接呈现的现象，例如“某些较长 GPU 区间出现后，短请求下一次输出延后”。解释是你提出的因果假设，例如“长 prefill 占用了执行时间”。方案是你打算如何干预，例如“限制单次为长 prefill 分配的 token 数”。

三者不能合并成一句“因为 prefill 太大，所以调小就会好”。这样会把尚未验证的原因变成结论，并忽略其他解释。

用一张小表记录：

| 层次 | 这次案例中的写法 |
| --- | --- |
| 观察 | 混合负载时短请求尾部生成间隔增大 |
| 初步证据 | trace 中相关时间段出现较长 prefill 执行 |
| 假设 | 大块 prefill 阻塞了短请求下一轮 decode |
| 干预 | 在实验策略中限制长 prefill 的单次分配 |
| 预测 | 大区间缩短，短请求等待下降，长请求可能更晚完成 |
| 反证 | 实际分配与 prefill 区间均缩小，但短请求等待未改善：反驳它是当前主要瓶颈的判断 |

### 为什么至少准备两个替代解释

同样的“输出停顿”也可能由 CPU 准备输入、tokenization、网络缓冲或某个慢 rank 导致。提前列出替代解释，不是拖延实现，而是避免对最先想到的原因产生依赖。

例如替代解释 A 是网关缓冲。验证办法是对齐服务端发送时间和客户端接收时间。替代解释 B 是 CPU 调度间隙。验证办法是看 GPU 空闲区间与主机活动，而不是只看最耗时的 GPU kernel。

当数据更支持替代解释时，调整项目方向是合理进展。一个被证伪的假设也有价值，只要你保留了实验条件和证据，而不是换一个说法继续宣布原判断正确。

### 在动手前定义什么叫成功

成功至少包含三类约束。第一是正确性：不能丢 token、串请求、泄漏缓存或破坏停止条件。第二是体验：目标请求的延迟达到预先定义的改善或 SLO。第三是代价：整体吞吐、长请求延迟和失败率不能超出允许范围。

不要等看到结果后再改门槛。例如原本希望长短请求都可用，测试后却只报告最漂亮的短请求数字，这会让结论失去可信度。

改善幅度也必须与自然波动相比。如果基线不同轮次波动 8%，候选只快 3% 一次，证据不够。可以增加重复、交错 A/B、控制缓存和背景负载，或选择更稳定的测量方法。

### 控制变量，不等于把世界假设成不变

固定模型、引擎、硬件和负载是为了提高可比性，但现实环境仍可能变化。记录设备温度/功耗状态、背景进程、服务错误以及实际请求完成情况，可以帮助解释异常。

尽量采用 A、B、A、B 的交错顺序，而不是上午跑完全部 A、晚上跑全部 B。如果中间机器负载改变，后者更容易把环境差异当作策略收益。

先保留所有原始数据，再按预先规则处理无效轮次。不要静默删除慢结果。若某轮外部网络故障，应说明它为何不符合实验条件，而不是因为它不利于候选就排除。

### 范围怎样控制到能真正交付

第一份 patch 只做一个机制：例如限制某类 prefill 的单次分配，并保留默认路径。先不同时加入动态预测、用户分级、复杂公平性和多机调度。

如果实验发现模型主要受 EP 偏斜影响，则可以换成专家负载观测项目，但要重写提案，让问题与最终改动一致。不要保留一个已经不对应代码的标题。

边界写得越清楚，验证越容易穷尽。例如明确仅用于某个文本模型和固定引擎版本，就比声称“通用加速所有模型”更接近真实可交付成果。

### 一份完整提案的示例骨架

问题是混合负载下短请求输出出现长尾。当前证据是请求时间线与 prefill 区间相关，但 CPU 与网络因素尚需排除。候选策略限制单个长 prefill 的分配，目标是增加 decode 获得执行的机会。

验证分两步：先加低开销统计确认机制，再关闭详细统计做性能 A/B。正确性检查覆盖取消、预算边界和缓存耗尽。性能检查同时看短请求 ITL、长请求 TTFT、吞吐与成功率。策略默认关闭，配置为默认值时恢复原行为。

这段提案还没有声称一定加速。它给出了值得检验的原因、实施位置和失败条件，足以开始下一课的代码工作。

### 练习与参考判断

试着写出一条会推翻自己假设的结果。如果你写的是“只要没有变快就继续调参”，它还不是反证。更好的写法是“分配上限确实减少了实际 prefill 区间，但短请求延迟不变，说明这一机制不是该负载的主要原因”。

再检查提案是否能让另一位同事独立复现。如果他还需要问你用哪个 commit、哪个数据集、哪个时间窗口，就补上这些信息。

下一课从这份提案出发，写出最小策略函数，并讲清楚为什么一个正确的小函数仍然不能直接冒充真实引擎的完整 patch。
