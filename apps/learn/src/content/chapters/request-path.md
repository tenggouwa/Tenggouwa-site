### 带着问题进入源码，而不是从第一个文件开始读

上一阶段，你已经能区分端到端等待和 GPU 执行，也能从 trace 提出假设。现在我们沿用“长文档与短对话混跑，短请求出现卡顿”的案例：如果证据指向引擎内部，下一步该读哪里？

源码阅读最容易走入两个极端：只查启动参数，停在表面；或者顺着 import 无限展开，几小时后忘了原来的问题。本课选择第三种方式：只追踪一次请求在不同模块之间的变化，先建立职责地图。

以下以 vLLM 的概念结构为例。具体文件、进程与调用方式随版本改变，课程不会把某个 main 分支路径当成永久接口。你最终记录的是“固定 commit 中的实际入口”，而不是背类名。

### 先确认你读到的代码，就是你运行的代码

容器中的 Python 包可能不是宿主机当前 checkout；一个 editable install 也可能指向另一个目录。源码看起来修改成功而运行行为完全不变，常见原因就是这两者没有对齐。

在实验环境记录三个身份：源码 commit、实际导入包位置、服务运行镜像或环境。进入引擎仓库后可以先运行：

```bash
git rev-parse HEAD
git status --short
python -c "import vllm; print(vllm.__version__); print(vllm.__file__)"
```

这些命令是核对证据，不代表你的当前教材项目已经安装 vLLM。不要在教材目录照搬后就假设正在读实际引擎源码。先准备独立的引擎实验 checkout，并按它的开发文档建立环境。

### 把一次请求看成一串状态变化

用户发送文本后，前端要校验参数、处理模板和 tokenization，形成模型可消费的 token IDs。引擎还要记录请求 ID、采样配置、已经处理到哪个位置、已生成多少 token、是否取消或结束。

请求刚进入时通常还不能立即占用 GPU。它可能等待调度和 KV 空间。Scheduler 决定某一轮给哪些请求安排多少 token；Model Runner 再把这些决定组织成设备张量，调用模型。

模型执行得到 logits，采样或其他输出逻辑产生 token；结果更新请求状态。如果满足停止条件，就释放对应资源并结束；否则留在后续迭代中。这里有多个异步边界，概念上的箭头不等于一次同步函数调用。

```text
文本与生成参数 → token IDs 与请求状态
             → 调度决定与缓存分配
             → 模型输入张量 → 模型执行 → 输出处理
             → 更新请求状态 → 完成或进入下一轮
```

### 五个职责，分别带着什么问题去找

| 职责 | 关心的数据 | 阅读时要回答的问题 |
| --- | --- | --- |
| API/输入处理 | 文本、模板、采样配置 | 参数何时校验？哪里变成 token IDs？ |
| 请求与调度 | 已处理位置、等待/运行集合 | 谁决定本轮 token 数？谁处理取消？ |
| KV 管理 | 逻辑位置、块表、引用 | 空间不足怎么处理？谁释放？ |
| Worker/Model Runner | 张量布局、设备、执行状态 | 谁准备 batch？哪里调用模型与 backend？ |
| 输出与生命周期 | logits、token、停止条件 | 什么时候算完成？错误如何回传？ |

这张表的价值是把“谁知道什么”分清楚。比如想按请求剩余 prefill 数调整预算，调度层通常更接近这个信息；一个只看到局部矩阵指针的 kernel 未必知道请求的用户优先级。

### 沿一个请求做最小取证

先用单个短请求或离线生成，减少并发干扰。给这个请求使用可识别但不含敏感信息的 ID。在关键边界记录：进入、入队、首次被调度、本轮 token 数、执行结束、完成或取消。

不要在每个 token 的热路径同步打印大量文本。日志本身可能成为瓶颈。先抽样一个请求，或使用计数器、轻量事件与 profiler annotation，测量观测开销。

记录中尽量不放用户原文。对于本课目标，token 数、状态、时间和匿名请求 ID 通常已经足够。每次看一个新函数，就写一句它接收什么、返回什么、修改谁的状态。

### 从函数名到调用链，怎样避免迷路

你可以先搜索职责，再查看调用者。例如在固定版本中搜索 `Scheduler`、`KVCacheManager`、`execute_model`、`add_request` 等关键字。搜索命中只提供候选入口，不等于运行时一定走到那里。在引擎仓库根目录可以运行下面的命令；若未安装 ripgrep，也可以使用编辑器的全局搜索。

```bash
rg -n "class Scheduler|class KVCacheManager|def execute_model|def add_request" vllm
```

先阅读命中位置的函数签名，再用同一个名称找调用者。不要求这条搜索在所有版本中命中全部职责；若名称变化，就沿上一节的输入输出继续定位。首次学习可以先完成静态职责地图，将实际调用和取消验证标为待实验环境验证；第 17 课再将地图用于改动和集成回归。

如果一个接口有多个 backend，要继续看注册、配置选择与设备分支。你读到的 CUDA 实现，可能在当前 CPU 环境根本不会被调用。验证最简单的方法是在实验环境加入低频标记，或者用 trace/断点确认实际调用。

把调用链限定在一条路径：先理解默认单卡、普通文本请求，再增加多卡、推测解码或多模态。每次只增加一类变化，否则难以分辨是哪种机制引入复杂度。

### 请求取消，比正常完成更能检查你是否读懂

正常完成通常走一条清晰路径；取消可能发生在等待、已分配缓存、GPU 正在执行或结果尚未返回时。如果你无法说明这些情况下资源由谁回收，就还没有完全理解生命周期。

这里要区分逻辑取消与设备任务立即停止。GPU 已提交工作可能不会因为用户断开连接立刻中断；引擎需要在合适边界丢弃输出、更新状态并安全释放资源。具体协议以实现为准。

练习：对同一个请求画出正常完成和取消两条路径。参考思路是标出“状态改变”和“物理资源可回收”两个时刻，它们不一定相同。然后用一个可控取消请求验证日志顺序。

### 你的第一份源码地图应该多大

不用画整个项目。先交付一页：五个职责、对应文件/函数、重要输入输出、跨进程或设备边界，以及一条实际请求证据。遇到不确定的路径标“未确认”，比猜测补齐更有价值。

如果你现在已能解释“这个配置影响哪层，哪层知道哪些状态”，就可以开始做有范围的改动。下一课聚焦调度：面对一个长 prefill 和几个正在 decode 的请求，引擎应该如何分配一轮有限的计算预算？
