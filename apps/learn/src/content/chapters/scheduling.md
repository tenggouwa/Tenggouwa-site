### 一个长请求，为什么会影响别人的输出

沿用贯穿案例：请求 A 正在输出短对话，请求 B 突然带着一篇长文档进入。A 下一步只需要生成一个 token，B 却有大量 prompt token 尚未处理。GPU 可以执行很多并行工作，但不能让所有工作都免费同时完成。

Scheduler 的职责是在资源和依赖约束下，决定下一轮做哪些工作。它面对的不只是“先来先服务”，还有 token 预算、KV 空间、请求状态和输出体验。本课先用一个小模型理解权衡，再说明怎样把它变成真实引擎实验。

### 为什么批次不能永远保持不变

静态 batch 可以一次收集几个请求，一起运行直到全部结束。若 A 只生成 10 token、B 生成 100 token，A 完成后的位置可能难以被新请求及时利用，或者需要额外机制避免浪费。

Continuous batching 在迭代边界重新组织活跃请求：完成的离开，符合条件的新请求加入。因此 batch 是一个随时间变化的集合，不必在一批请求全部完成后才接下一批。

但这并不代表随时都能插入。引擎仍要组织形状、维护状态并遵守执行边界。你看到的最大并发请求数，也不等于每轮真的有那么多请求参与 GPU 计算。

### 请求预算与 token 预算有何不同

两个请求可能都只占一个“请求槽”，但一个有 32 个输入 token，另一个有 32768 个。只限制请求数无法描述这一轮工作的大小。

许多调度设计会限制每轮总 token 数。例如预算为 512，而若干 decode 请求各需要少量新 token，剩余预算才可以用于 prefill。实际实现可能采用统一 token 计数，不一定有两个完全独立的队列算法。

token 数是可操作的代理指标，不是精确运行时间。128 个 prefill token 与 128 个不同请求的 decode token，形状和历史读取可能不同，执行成本也不同。先用预算控制工作粒度，再用时间线确认效果。

### 用本页模型手算两种调度

教学模型有一个 2048-token prompt，还有另一个正在 decode 的请求，需要继续输出 16 步。我们人为规定：每 prompt token 花 0.02 ms，每次 decode 花 1 ms，每轮调度开销 0.4 ms。每轮先做一块 prefill，再做一个 decode。

若 chunk=2048，第一次 decode 前先等 `0.4+2048×0.02` ms，它在 42.36 ms 结束。若 chunk=128，则第一次 decode 在 `0.4+128×0.02+1=3.96` ms 结束。把 prefill 切小后，decode 更早得到执行机会。

不过长 prompt 的完成时间发生了反向变化。chunk=2048 时 prefill 在 41.36 ms 完成；chunk=128 时中间穿插了许多 decode，prefill 到 62.36 ms 才完成。你改善了短请求的等待，也让长输入的初始处理拖得更久。

本模型中的总轮数在这些参数下都由 16 步 decode 限制，所以总时间可能相同。这并不证明真实引擎切分没有额外吞吐代价；真实成本还取决于形状、启动、缓存和并行效率。页面特意展示这一点，避免把线性模拟当硬件预测。

### 更小的 chunk 为什么可能更慢

每块工作太小时，固定的 Python 调度、输入准备和 kernel launch 开销占比会变大。矩阵形状也可能从高效区间变成低效区间。过多切分还可能影响图执行、缓存访问或内部流水。

所以优化目标通常不是把 chunk 调到最小，而是在短请求体验、长请求完成时间和总吞吐之间找到符合目标的选择。先明确你的 SLO（服务目标，例如某类请求的 P99 延迟上限）：是 TTFT 必须低于某个值，还是正在输出的请求不能长时间卡住？不同目标可能对应不同策略。

### 饥饿，是优先级策略必须回答的问题

假设你总是优先满足 decode，而新 decode 请求不断到来。长 prefill 如果持续拿不到预算，就可能长期无法前进。这叫饥饿。

可考虑的机制包括保留少量 prefill 预算、等待时间加权或限制某类工作连续占用。但这些不是可以随意叠加的开关，每个机制都会带来额外状态和测试需求。你的第一个 patch 先解决一个明确机制，不要一次设计完整的多租户调度平台。

阅读真实源码时，至少找出三个约束：本轮预算从哪里来，KV 不足时如何处理，等待很久的请求如何重新获得机会。任何新策略都必须仍然尊重它们。

### 一份可以验证的 A/B 应该怎么写

基线 A 和候选 B 使用同一模型、同一引擎 commit、同一请求到达序列、同一输入分布和输出条件。B 只改变你正在研究的 chunk/预算策略。

先用低开销事件证明 B 确实改变了每轮分配；再用 trace 检查预期的长 GPU 区间是否缩短。最后在无详细插桩时测短请求 ITL、长请求 TTFT、整体吞吐和失败率。不能只挑一个改善最明显的指标。

至少测试纯短、纯长、混合、接近容量四种场景。若混合场景变好、纯长吞吐显著下降，报告必须说明该策略的适用范围，而不是把所有结果合并成一个平均加速比。

### 练习与参考分析

先运行 `python3 labs/scheduler_reference.py --chunk 128 512 2048`。在看输出前写下你预计哪种参数让 decode 首次等待最短，哪种让 prefill 最早完成，再核对。

再回答：如果调小 chunk 后，短请求仍然卡顿，是否继续调到更小？参考分析是先看机制证据。如果真正等待发生在网关，或者 CPU 准备输入的时间占主导，继续缩小 GPU 工作块可能没有作用，甚至更差。

下一课解释一个会直接改变可调度性的资源：KV Cache。即使本轮还有计算预算，也可能因为没有合适缓存空间而无法让新请求前进。理解调度与内存之间的接口，才能安全改策略。
