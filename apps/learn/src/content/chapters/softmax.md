### 为什么选择 Softmax 作为第一个融合算子

Attention 课已经出现过 Softmax；现在我们知道它的数学作用，也知道 GPU 的数据搬运有成本。这个算子足够简单，可以把“公式正确”和“执行高效”放在同一个小实验里讨论。

本课的目标不是做通用生产库，而是读懂、运行并修改一个有限范围的 Triton kernel。支持范围是有限数值、二维连续输入、列数不超过 4096。超出范围需要另外设计，不要默默扩大适用结论。

### 从数学步骤数出中间读写

对一行 x，稳定 Softmax 是先找最大值 m，再算 `p=exp(x−m)`，最后输出 `p/sum(p)`。如果这些步骤分别产生保存在 HBM 的中间数组，就会出现多次 kernel launch 和中间读写。

融合实现希望把这一行加载后尽量留在片上，完成 max、减法、exp、sum、除法，再把结果写回。理论上减少了中间数据流量和启动次数，但并不意味着框架基线是“最朴素的五个 kernel”：成熟的 torch.softmax 自己也可能已经高度优化。

因此我们比较的是具体实现，不是拿一个故意低效的基线保证胜利。最快结果依赖形状、dtype、设备与编译配置。

### 把数学翻译成一个 Triton program

课程文件 `labs/triton_softmax.py` 使用一行对应一个 program。`program_id(0)` 决定行号，`arange(0,BLOCK)` 产生列索引，指针 `X+row*N+cols` 指向该行的数据。

为方便 reduction，BLOCK 取覆盖列数的 2 的幂。若实际有 1000 列，BLOCK=1024，需要给多出的 24 个位置正确的填充值。

关键部分如下，是下载脚本中 kernel 的核心，不是一个可以脱离 Triton 环境独立运行的普通 Python 函数：

```python
cols = tl.arange(0, BLOCK)
x = tl.load(X + row * N + cols, mask=cols < N,
            other=-float('inf')).to(tl.float32)
p = tl.exp(x - tl.max(x, axis=0))
y = p / tl.sum(p, axis=0)
tl.store(Y + row * N + cols, y, mask=cols < N)
```

读时填 `-inf`，因为它不会成为有限行的最大值，取 exp 后又是 0，不会影响分母。写时必须再次 mask，防止越界。把输入提升到 FP32 用于这些中间计算，有助于控制较低精度输入下的数值误差；最终写入按输出 dtype 转换。

### 填充值错了，会产生什么结果

假设有效分数都是负数，补齐位置却填了 0。最大值就可能来自无效位置；即使最大值平移本身不改变理论归一化，无效位置的 exp 还会加入分母，导致有效输出的和小于 1。

如果你只用正数或只测列数正好是 2 的幂，可能长期看不出错误。这就是为什么测试必须覆盖非整除形状和不同数值范围，而不只是默认随机输入。

另一类错误是写越界。输出看起来正确并不能证明没有损坏相邻内存。实际 kernel 开发还应结合合适的设备检查工具和边界用例，而不是用一次成功运行作为证明。

### 正确性应该如何比较

使用 `torch.softmax` 作为参考，对多个 shape 和 dtype 做比较。FP32 可以用较严格的绝对/相对容差；FP16 需要考虑表示精度。接近 0 的参考值只看相对误差会很不稳定，因此通常同时使用 atol 和 rtol。

本课程脚本覆盖四组形状、两种 dtype，并分别测试正常尺度和较大输入尺度。它会先执行数值断言，再做 benchmark。所有输入假定有限，不声称覆盖 NaN/Inf 等特殊语义。

你还可以检查每行和接近 1、输出非负、同一行平移常数后基本不变。这些是有助于定位错误的不变量，但不应替代与独立参考的完整比较。

### 为什么运行前要先编译和预热

Triton 需要为相应形状和配置编译 kernel。第一次调用的时间可能包含编译、初始化和缓存准备，不代表持续执行成本。Benchmark 工具通常会做预热与重复测量；仍需记录具体版本和使用方式。

本课同时测 torch 和 Triton，用相同输入与可比条件。若只测一次且 torch 先运行、Triton 后运行，你还可能把缓存状态和初始化差异当成算法收益。

不要同时运行多个重负载实验再比较微秒级结果。对于短 kernel，计时误差和背景活动很容易掩盖真实差别；先看稳定分布，再解释小幅变化。

### 第一次修改 num_warps，应该期待什么

更多 warp 可能提供更多执行并行度，也可能增加协调、资源竞争或不必要工作。对于很短的行，launch 开销可能比算术本身更重要；对于很长的行，片上资源需求又可能成为限制。

固定输入，只改 num_warps，并为每个配置重新运行全部数值测试。记录每种 shape 的基线时间、候选时间和加速比。发现某些 shape 退化时，要保留它们，不能只展示赢的部分。

如果你想做配置选择，先把“根据 shape 选配置”的规则写清楚，再用未参与选择的形状检查。否则容易把一次特定机器上的偶然最优值写死。

### 从单算子收益走回服务

假设 Softmax 自身快了 2 倍，但只占服务关键路径 1%，整体收益会非常有限。下一课会用 Amdahl 定律算清这个上限。

本课验收应包含正确性结果、不同形状的时间以及失败/退化记录。GPU 不可用时可以完成数学和索引推导，但数值与性能结果要标为未测。页面里的模拟不能替代这段真实 kernel 的执行。

思考题：一个融合 kernel 少读写了数据，却比 torch 慢，有没有矛盾？没有。Torch 可能使用更好的已有实现；你的映射、资源使用或小规模开销也可能抵消流量减少。这个反例正是继续学习 GPU 工程的入口。
