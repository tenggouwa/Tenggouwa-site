### 最后的目标，是形成别人能够复现的结果

你最初的目标是从部署和调参，逐步走到理解模型与引擎、能够做定制优化。现在我们用一个毕业项目把这些能力连起来：选择真实瓶颈，定位代码，完成范围明确的改动，再证明正确性和收益边界。

这不要求你发明一种新 Attention 算法。一个针对特定负载有效、实现可靠、解释清楚的调度 patch，就是完整的系统工程成果。反过来，即使改了很多 CUDA 代码，如果没有可比较的基线和正确性证据，也还没有完成交付。

### 你的项目应该有一个明确起点

继续采用长短请求混跑案例，或选择你实际遇到的 kernel 热点、EP 偏斜、推测解码收益问题。只选一个主问题，写清受影响用户、工作负载和衡量方式。

环境必须能被重新建立：模型 revision、引擎 commit、依赖、硬件、启动命令和数据准备步骤。私有数据需脱敏或提供能复现关键现象的替代集，并说明替代集的边界。

没有 GPU 时，可以先完成教材和 CPU 实验、读源码、准备 patch 与测试，但最终性能结论应标“待 GPU 验证”。项目完成与否由证据决定，不由网页进度条决定。

### 一份交付包可以这样组织

```text
my-optimization/
  README.md              # 问题、环境与一条完整复现路径
  proposal.md            # 假设、反证、预设验收目标
  patch.diff             # 或可获取的实验分支 commit
  workload/              # 可复现数据生成方式与 seed
  commands/              # baseline / candidate 命令
  raw/                   # 每轮逐请求数据及错误记录
  traces/                # 解释机制的 trace
  correctness/           # 数值、生命周期、边界测试
  report.md              # 汇总、适用范围、回退
```

文件名不是强制标准，关键是别人不需要从聊天记录里拼凑步骤。若某项依赖内部环境，明确写出需要的访问条件，不把缺失凭据隐藏成“运行即可”。

### 用一个虚构对照表学习怎样下结论

下面全部是教学虚构数据，只用于示范报告解释，不能作为任何模型的实测结果。假设我们的候选策略在不同负载下得到：

| 工作负载 | 策略 | 短请求 P99 ITL | 长请求 P99 TTFT | 输出吞吐 |
| --- | --- | --- | --- | --- |
| 长短混合 | 默认 | 120 ms | 1.2 s | 1000 tok/s |
| 长短混合 | 候选 | 75 ms | 1.5 s | 960 tok/s |
| 纯短 | 默认 | 45 ms | 不适用 | 1100 tok/s |
| 纯短 | 候选 | 45 ms | 不适用 | 1095 tok/s |

混合负载中，短请求尾部间隔下降了 37.5%，但长请求 TTFT 增加 25%，吞吐下降 4%。这不是“整体快了 37.5%”。是否可以接受，取决于实验前约定的目标和代价上限。

如果业务要求长请求 TTFT 不得超过 1.4 秒，候选即使改善短请求，也没有通过当前验收。如果长请求可接受 1.6 秒且吞吐允许小幅损失，它可能是适合这个负载的选择。数字需要放回需求中解释。

### 一张表还不足以证明因果

你还要展示机制证据：候选是否确实减少了单次 prefill 分配，trace 中大区间是否缩短，短请求等待是否与之对应。只有汇总表，很难排除缓存命中、实际输出变短或机器负载变化。

同时给出样本量、重复轮次、波动和失败率。至少三轮可以作为入门起点，但高噪声或严格统计结论可能需要更多。报告平均值时也保留各轮原始值，不把异常隐藏起来。

若某轮失败率升高，解释其原因以及是否满足验收。延迟分位数可以单独统计成功请求，但必须同时报告失败率和超时；不能只呈现成功子集而隐藏未完成的请求，从而让较差版本看起来延迟更低。

### 正确性报告应该回答哪些问题

对调度改动，确认请求没有丢失或重复、已处理位置一致、取消和抢占后的资源回收正确；对 kernel 改动，确认 shape/dtype/边界的数值误差；对量化或采样相关改动，补充相应质量或分布检查。

明确列出未覆盖范围。只验证一个 dense 文本模型，不能声称所有 MoE、多模态和推测路径都可靠。已知限制有助于安全使用，不是需要藏起来的缺点。

默认开关关闭时也应有测试结果；回退不只是配置名称，而是恢复后确认行为和指标的具体步骤。

### 五个答辩问题，逐个用证据回答

第一，你优化的是哪一段关键路径？用调用链与 trace 指出位置，不要只回答“GPU”。

第二，为什么认为它是瓶颈？给出受控观察，并说明排除了哪些替代解释。

第三，为什么改动不会破坏正确性？展示真正会捕获错误的测试和适用范围，而不是只说“运行没报错”。

第四，收益在什么条件下成立？说明硬件、模型、版本、shape、负载和退化场景，不只展示最佳结果。

第五，别人怎样复现和撤回？提供命令、数据生成、patch 身份和恢复步骤；让一份干净 checkout 跑通核心流程。

### 当结果没有加速，你仍然可以交付什么

如果假设被推翻，保留基线、反证和对真正瓶颈的进一步定位。这是一份有价值的研究记录，但不能命名为“性能优化已成功”。

可以缩小适用范围或修改方案，再重新对照原目标。如果最终只完成观测工具，就把交付标题改成观测与诊断，不把计划中的优化写成已实现。

这也适用于我们的教学策略函数：它是练习与实验起点，只有接入固定引擎、通过测试并获得真实数据后，才能讨论引擎级收益。

### 如何确认自己跨过了部署与定制之间的那一步

回看起点，你以前主要知道哪个开关可能有效。现在应该能够解释它改变哪段计算、内存或调度机制，预测什么条件下可能有效，并找到源码中的对应入口。

当预测不成立时，你能用 trace 和数据调整判断；当需要改动时，你能保留默认行为，编写测试，说明收益与代价。这些能力才是本课程想建立的积累。

完成报告后，在本课笔记链接或写明证据文件位置，再填写自评验收。后续可以从你最有兴趣的一条分支继续深入：调度与缓存、GPU kernel、分布式通信或推测执行。无需同时精通所有方向，但每次深入都沿用同一套“理解 → 假设 → 实现 → 验证”的方法。
