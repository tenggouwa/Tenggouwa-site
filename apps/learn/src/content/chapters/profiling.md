### 你有了慢的数字，还缺慢的位置

基线告诉你“长短请求混跑时，短请求的生成间隔变差”；Roofline 给你一些资源瓶颈假设。但现在至少有三种解释：GPU 被长 prefill 占用，CPU 没及时提交下一轮，或者多卡在等待某个慢 rank（这里先理解为参与计算的某个进程，第 13 课再解释分组）。

Profiling 的任务是把这些解释放到执行证据上。它不是收集一张复杂截图，而是找出影响完成时间的关键路径，并为下一次单变量实验提供依据。

这里先学习一个本地 toy workload，再迁移到模型服务。CPU 也能完成第一步，不需要等你拥有一台专用 GPU。

### 三种工具各自回答哪一层问题

PyTorch Profiler 能把高层算子名称、形状、CPU 活动和设备活动关联起来。你可以看到 `aten::mm`、Softmax 等操作，而不必先读所有底层 kernel 名。

Nsight Systems 更适合观察系统时间线：主机线程何时提交，GPU 何时执行，通信与计算是否交叠，哪里存在等待和空洞。

Nsight Compute 则用于已经确认的具体 kernel，查看访存与计算指标、资源使用以及性能限制。它不是第一步就扫描一切的工具，因为详细 profiling 可能明显扰动执行。

使用顺序通常是“整体时间线 → 热点操作 → kernel 内部”。如果瓶颈在 Python 准备输入，先研究某个 Tensor Core 指标不会直接解决问题。

### CPU 提交完成，不等于 GPU 工作完成

假设 Python 调用一个 CUDA 矩阵乘法。常见执行方式是把任务提交到 CUDA stream（设备工作的有序提交队列）后返回，GPU 稍后执行。你在 Python 调用前后用计时器相减，可能主要量到提交时间。

为了测一段 GPU 工作的端到端耗时，可以在测量前确保先前工作结束，测量后等待这段工作完成。CUDA Events 可以量同一 stream 上的设备时间；选择哪种方式取决于你要包含哪些开销。

但不要在每个操作后都加同步。原本可重叠的工作会被你强行串行化，最后量到的是被测量手段改变过的程序。

```python
# 测量边界示意，需要 CUDA 环境
import time
import torch

torch.cuda.synchronize()
start = time.perf_counter()
# 在这里执行一整段待测 GPU workload
torch.cuda.synchronize()
elapsed = time.perf_counter() - start
```

这不是完整 benchmark：还需要预热、多次重复、明确输入和避免把 profiler 本身的开销混进结论。

### 跑第一份可以自己解释的 trace

本项目的 `labs/torch_profile.py` 只做一个 512×512 矩阵乘法，再做逐行 Softmax。它先固定随机种子、预热五次，再在未启用 profiler 时测二十次，之后单独采集五次执行的 trace。

在项目根目录运行：

```bash
work/lab-venv/bin/python labs/torch_profile.py \
  --device cpu --output work/trace-cpu.json
```

如果虚拟环境不存在，先按 README 安装 PyTorch。NVIDIA 实验机可将设备改为 `cuda`。不要把 CPU 与 GPU 结果直接用来评价真实模型服务，它们只是帮助你学习同一套观察方法。

终端表中的 Self CPU 是操作自身在主机侧归属的时间，CPU total 可能包含子操作。嵌套区间的 total 不能随意相加，否则会重复计数。异步设备执行还要到 GPU 对应轨道看，而不是只读 CPU 表。

Trace 文件可以在支持 Chrome trace 格式的查看器中打开。先找到 `toy_linear_softmax` 区间，再看它包住了哪些操作，最后对应到脚本中的两行计算。

### 一张时间线应该怎样读

第一遍只看空闲和忙碌。若 GPU kernel 之间有大间隔，问：CPU 此时在准备输入、等待 IPC（进程间通信），还是做同步？若 GPU 连续忙，再看哪段计算占据了关键路径。

第二遍看重复结构。Decode 常出现逐轮相似的模式；某一轮突然拉长时，检查是否插入了 prefill、缓存管理、形状变化或编译。把异常区间与请求、token 数和调度事件对齐，比只记录“有一条很长的条”更有用。

第三遍看重叠。通信 kernel 持续 3 ms，如果它和 3 ms 计算充分重叠，暴露到完成时间上的通信代价可能小于 3 ms。反过来，一个 rank 晚到 collective（多个进程共同参与的数据交换或归约操作），也可能让别的 rank 看起来“通信很慢”。

关键路径指决定这轮最早何时能完成的依赖链，而不是简单把所有设备上的 busy 时间相加。

### 用观察写出可以验证的假设

假设 trace 显示，每当长 prompt 到达，短请求下一次 decode 前都会等待一个较长 GPU 区间。你可以写：“长 prefill 的单轮执行阻塞了 decode，缩小 prefill chunk 可能改善短请求的生成间隔。”

如果看到的是 GPU 空闲、CPU 在长时间整理输入，就应换成另一个假设。两者可能产生相似的用户症状，却需要修改完全不同的地方。

验证时一次只改一个条件。例如只降低 chunk 预算，保持请求到达顺序和输出要求一致；然后观察预测的 GPU 区间是否缩短，同时检查长请求是否变慢。如果用户延迟改善，但预期区间没变化，要继续寻找真正原因。

### 常见的三种误读

第一，把 GPU utilization 高当成有效计算多。这个指标不能告诉你执行的工作是否有用、是否受带宽限制、是否在等待依赖。

第二，把 profiler 下的总耗时当最终性能。插桩、采样、计数器收集可能有额外代价；最终 A/B 应在正常配置下测量，profile 用于解释。

第三，只看最快一次。编译、缓存、温度、功耗状态、背景进程和 CPU 调度都可能造成波动。保留每轮结果，说明预热与测量边界。
